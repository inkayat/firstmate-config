# Django backend

Work the way the project already works; this skill fills gaps, it never
overrides the project's own instructions or conventions.

## Before editing

1. Find the project's entry points: `manage.py`, the settings module
   (`DJANGO_SETTINGS_MODULE`), `INSTALLED_APPS`, URL roots, and how tests run
   (`manage.py test`, `pytest`). Use the project's interpreter or virtualenv,
   never a global one.
2. Read the model, its migrations directory, the serializer, the view, the URL
   wiring, and the existing tests for the area you touch.
3. Note the authentication and permission classes in force - the
   `REST_FRAMEWORK` settings and any per-view overrides - before adding an
   endpoint.

## Models and migrations

- Every model change ships with a migration generated by
  `manage.py makemigrations <app>`; read the generated file before keeping it.
- Never edit a migration that may already be applied elsewhere; add a new one.
- A new non-null field on an existing table needs a `default` (or a nullable
  step plus a data migration); say which and why.
- Data changes go in a data migration with `RunPython` and a reverse function,
  using `apps.get_model`, never the imported model class.
- Before finishing, `manage.py makemigrations --check --dry-run` must report no
  changes, and `manage.py migrate` must run cleanly on a fresh database.

## Querysets and data access

- Scope every queryset to what the caller may see in `get_queryset`, not after
  fetching: an object the user does not own should be a 404, not a 403 that
  confirms it exists - unless the project already does otherwise.
- Avoid N+1 queries: use `select_related` for forward foreign keys and
  `prefetch_related` for reverse or many-to-many relations used in a list.
- Keep ordering explicit (`order_by`) wherever the API promises an order.
- Wrap multi-write operations that must succeed together in
  `transaction.atomic()`.

## DRF serializers and views

- Validate input in the serializer (`validate_<field>`, `validate`); keep views
  thin.
- Make server-controlled fields read-only (`read_only_fields`) so clients cannot
  set owners, timestamps, or state they should change only through an action.
- For a state change that is not a plain field edit, prefer an explicit
  `@action(detail=True, methods=["post"])` with its own permission check.
- Keep the project's error format; DRF's default is `{"detail": "..."}` for
  non-field errors.
- Unauthenticated requests get 401 only when the first authentication class
  defines `authenticate_header`; otherwise DRF returns 403. Match what the
  project's clients expect.

## Tests

- Use the project's test style; with DRF, `APITestCase` and
  `self.client.force_authenticate(user)` cover views without real auth flows.
- Test what a client observes: status codes, response bodies, ordering, and that
  another user's data is invisible and unchangeable.
- Run the full backend suite and the migration check before declaring done, and
  report the exact commands and their output.

## Security defaults

Never weaken `ALLOWED_HOSTS`, CSRF, or authentication settings to make a test
pass. Never put secrets in settings files or fixtures. Raw SQL only with
parameters, never string formatting.
