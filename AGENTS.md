# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `README.md` is the project-level source of truth: layout, install, the multi-project Captain model, and routing. Read it first.
- The Captain's project-selection precedence ("which project", the launch-directory hint, and why a project's instructions/skills are never preloaded at startup) is owned by `firstmate/primary-policy.md` section 1; do not duplicate it here.
- The delegated-worker context/skill-class contract (why Pi and OMP need an explicit compact handoff instead of "the harness discovers project instructions natively", the three skill populations - official FirstMate internal, firstmate-config shared worker, project-local - and the required per-task path/precedence handoff) is owned by `firstmate/primary-policy.md` section 2 and README.md "Worker context and skill classes"; do not duplicate it here.
- Tests: `tests/install-launch.sh` (fixture-isolated install, idempotence, foreign links, Pi/OMP launch), `tests/update.sh` (offline local Git origins and update refusals), `tests/standalone-contract.sh` (standalone root guards, read-only verify and machine-owned state preservation), `tests/worker-context.sh` (worker context handoff: offline fixture plus Pi native-loader probe, never a substitute for a live delegated Pi/OMP fixture run), `tests/routing-trace.sh` (the temporary Captain routing/skill trace of `firstmate/primary-policy.md` section 0: offline fixtures plus a real `bin/fm-spawn.sh` seam with a fake `omp`, SKIP without `tmux`/`treehouse`; its `check` CLI is a diagnostic, never a gate or monitor; keep that trace contract as section 0 near the top of the policy - a live Captain run showed its default OMP read stops at line 300 and never reached it when it was the last section).
- `roles/manifest.json` (each role's mode, what it may change, the final blocks it can end with, the sub-agent call graph) and `workflows/selection.json` (which workflow each kind of task must run; the closed exception list) are the single sources behind the role army and the forced-workflow rule; role frontmatter (`spawns`, `tools`) mirrors them and `bin/fm-workflow check` (run by `tests/workflows.sh`) rejects drift, while policy section 4 and the `README.md` role table mirror them and `tests/roles.sh` rejects drift - never add a second table. The `result`/`verdict`/`risk` block formats live in `bin/fm-workflow`; every role example block must parse. `REVIEW.md` is this repository's diff-triggered review checklist, read from the base branch.
- Scripts under `bin/` and `tests/` must run under macOS `/bin/bash` 3.2 (no associative arrays, `${x,,}` or `mapfile`; no apostrophe inside a `$(cat <<'EOF')` heredoc). Offline suites: `tests/roles.sh`, `tests/workflows.sh` (engine, forcing rule, army check), `tests/retro.sh` (`bin/fm-retro`: the retro log, aggregation and proposals - proposals are never applied by a task), `tests/evals.sh` (failure-pattern evals) and `tests/workflows-live.sh selftest`; `tests/workflows-e2e.sh` SKIPs without `tmux`/`treehouse`.
- `firstmate/stack-manifest.tsv` is the single tracked source of truth for the official FirstMate repository, explicit branch and validated commit (see its header for deliberate exclusions). `firstmate/fm-stack-manifest.sh` is the one parsing/commit-comparison owner, sourced by `install.sh` and `bin/fm-update`; never duplicate its TSV parsing or commit comparison in a script or test - fixtures may generate alternate manifests, but assertions against the tracked manifest must load it dynamically (`stack_manifest_load`), never hardcode its values as separate literals.
- `data/projects.md`/`bin/fm-project-mode.sh` is a registered-**delivery-posture** lookup only, never a project resolver or location lookup (its own header, AGENTS.md section 7). Project name -> path resolution is `bin/fm-spawn.sh`'s own `projects/<name>` shorthand against `$FM_HOME/projects/<name>` - the one mechanism upstream provides; do not add a second one.
- `firstmate/fm-captain-lib.sh` owns Captain harness selection and availability for `bin/fm`; extend it rather than adding another detector. README.md's startup and "Captain startup model" sections own Pi-default / explicit-OMP behavior. OMP catalog probes must retain `--no-extensions`: native `models` otherwise binds factories and can overwrite live FirstMate markers. Actual Captain startup uses native project discovery, never the worker overlay.
- `firstmate/crew-dispatch.json` routes work through ten dispatch categories (QUICK, EXPLORE, RESEARCH, REVIEW, ARCHITECTURE, TENTH-MAN, IMPLEMENT, IMPLEMENT-LARGE, DEEP, UI/BROWSER) as twenty-seven `rules` entries plus the untagged `default` for the DEFAULT catch-all; `firstmate/crew-dispatch.json` owns the per-category sub-lane breakdown; `firstmate/primary-policy.md` section 3 owns its application contract. Routing is Opus 5.5-biased: substantive work ("substantive" as section 3 defines it) goes to Opus 5.5, bounded work may stay on Sonnet 5.5, trivial work on Haiku/Luna, and DEFAULT is Opus 5.5 high for the temporary routing-trace debugging period (section 0). Sub-lanes are separate same-category rules, never new categories; only QUICK and simple EXPLORE (Haiku/Luna) and the four IMPLEMENT/IMPLEMENT-LARGE rules (Claude candidate first, then OMP GPT-6.2 Sol at the same effort) carry a multi-candidate `use` array, so nothing else can be quota-selected ahead of an Opus 5.5 primary. `openai-codex/gpt-6.2-sol` is the everyday cross-family route (RESEARCH's Pi-tooling rule, REVIEW's cross-family second reviewer, DEEP's escalations, TENTH-MAN's Claude-primary rule, the IMPLEMENT/IMPLEMENT-LARGE GPT alternative, Captain startup's first preference); `openai-codex/gpt-6.2-astra` stays Pi-only and confined to each category's narrowest escalation. Preserve every category collision sentence.
- Bounded internal helpers remain supported by `firstmate/primary-policy.md` section 6: FirstMate owns macro orchestration; OMP's native `task` tool owns bounded task-local delegation. Pi has no bundled equivalent and stays not-applicable. `tests/worker-context.sh` provides `internal-prepare`/`internal-handoff` canaries inside the parent's worktree and `validate` report checks; corroborate reports with existing harness session evidence, not new telemetry. These checks do not enforce tool ordering or gate FirstMate completion; see README.md "Worker context and skill classes" and "Completion evidence limits".
- A checkpoint/ordering-gate experiment for target-discovery and a verification-provenance classifier were tried, then fully removed (see git history around "Remove abandoned provenance and checkpoint enforcement experiment"). `tests/worker-context.sh`'s `scope-prepare`/`scope-handoff`/`scope-validate` restore only the useful open-ended-discovery coverage from that removal (root-only launch scope, an independently selected nested candidate, body-only canary evidence that its instruction/skill were applied) - never read-order, tool-order, or completion-gate checks. Do not reintroduce that machinery.
- Adding or changing anything under `skills/*/SKILL.md` from a disposable task worktree does not install it: a worktree must not repoint the machine's shared `~/.agents/skills`. A real reconcile requires `./install.sh` (no `--verify`) from the primary checkout, never from a task worktree.
- `./install.sh --verify` is read-only and safe from a disposable worktree. Plain `./install.sh` links live commands, skills and dispatch at its checkout: run it only from the primary checkout, never a task worktree. Installer drift against primary-checkout paths is expected from a worktree.
