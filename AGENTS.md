# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `README.md` is the project-level source of truth: layout, install, the multi-project Captain model, and routing. Read it first.
- The Captain's project-selection precedence ("which project", the launch-directory hint, and why a project's instructions/skills are never preloaded at startup) is owned by `firstmate/primary-policy.md` section 1; do not duplicate it here.
- The delegated-worker context/skill-class contract (why Pi and OMP need an explicit compact handoff instead of "the harness discovers project instructions natively", the three skill populations - official FirstMate internal, firstmate-config shared worker, project-local - and the required per-task path/precedence handoff) is owned by `firstmate/primary-policy.md` section 2 and README.md "Worker context and skill classes"; do not duplicate it here.
- Tests: `tests/smoke.sh` (launcher/install/herdr), `tests/captain-harness.sh` (OMP default, explicit Pi fallback, native availability and diagnostic agreement), `tests/model-selection.sh` (Pi fallback's original model chain), `tests/multi-project-captain.sh` (project resolution, real `bin/fm-spawn.sh` dispatch/isolation, instruction/skill separation, Pi/OMP routing - requires `tmux` and `treehouse` on `PATH`, uses an isolated `TMUX_TMPDIR` server so it never touches the shared/live session), `tests/doctor.sh` (`fm doctor` statuses/exit codes/JSON schema, fully fixture-isolated - see its header for the hermetic PATH rationale), `tests/stack-manifest.sh` (shared parser/comparator plus fixture-isolated install/doctor/version scenarios, offline local Git origins), `tests/worker-context.sh` (worker context handoff: offline fixture plus Pi native-loader probe, never a substitute for a live delegated Pi/OMP fixture run), `tests/captain-review-scenarios.sh` (real, opt-in-live-only Captain independent-review-policy scenarios A-D via real `bin/fm-spawn.sh` dispatch of the real `omp` harness against a disposable local clone of official FirstMate with its remote removed; defaults to SKIPPED, never fabricates PASS on a missing prerequisite; scenario B is a real, reproducible, disclosed conflict between this repo's own `firstmate/primary-policy.md` "review required for substantive IMPLEMENT work" and official FirstMate AGENTS.md section 7's "no separate reviewer without an explicit captain request" - not a script bug, see the script's own header).
- `firstmate/stack-manifest.tsv` is the single tracked source of truth for stack compatibility (official FirstMate repo/validated commit, Pi/OMP/Herdr min/tested versions - see README.md "Stack compatibility" and the manifest's own header comment for what is deliberately excluded). `firstmate/fm-stack-manifest.sh` is the one parsing/comparison owner, sourced by `install.sh`, `bin/fm-doctor`, and `bin/fm-version`; never duplicate its TSV parsing or version comparison in a script or a test - fixtures may generate alternate manifests, but assertions against the real tracked manifest must load it dynamically (`stack_manifest_load`), never hardcode its values as separate literals.
- `data/projects.md`/`bin/fm-project-mode.sh` is a registered-**delivery-posture** lookup only, never a project resolver or location lookup (its own header, AGENTS.md section 7). Project name -> path resolution is `bin/fm-spawn.sh`'s own `projects/<name>` shorthand against `$FM_HOME/projects/<name>` - the one mechanism upstream provides; do not add a second one.
- `firstmate/fm-captain-lib.sh` owns Captain harness selection and availability, shared by `bin/fm`, `bin/fm-doctor`, and `bin/fm-version`; extend it rather than adding another detector. README.md's startup and "Captain startup model" sections own OMP-default / explicit-Pi behavior. OMP catalog diagnostics must retain `--no-extensions`: native `models` otherwise binds factories and can overwrite live FirstMate markers. Actual Captain startup uses native project discovery, never the worker overlay. Doctor's header owns its read-only mandatory-vs-advisory exit gate.
- `firstmate/crew-dispatch.json` routes work through eleven dispatch categories (QUICK, EXPLORE, RESEARCH, REVIEW, ARCHITECTURE, TENTH-MAN, IMPLEMENT, IMPLEMENT-LARGE, DEEP, UI/BROWSER, DEFAULT): twenty-six `rules` entries (ten distinct `category` values; EXPLORE, IMPLEMENT, IMPLEMENT-LARGE, and UI/BROWSER each span two more-specific rules sharing one category value; RESEARCH spans two; REVIEW spans four - ordinary, complex, high-risk, cross-family second review; ARCHITECTURE spans three - ordinary, exceptional (Opus 5.5/Sol quota peers), Astra ultra-exceptional; TENTH-MAN spans three - Claude-primary Sol, Astra critical/unresolved escalation, OpenAI-primary Opus 5.5; DEEP spans five single-candidate conditional rules - scout primary, scout Sol escalation, ship primary, ship Sol second-hypothesis, Astra exceptional last escalation) plus the untagged `default` catch-all for DEFAULT. FirstMate resolves a matched rule's `use` array through its quota-array procedure, so arrays hold only deliberate semantic peers: QUICK and EXPLORE's ordinary rule each pair Haiku/Luna, ARCHITECTURE's exceptional rule pairs Opus 5.5/Sol. DEEP, TENTH-MAN's Astra escalation, REVIEW's cross-family escalation, ARCHITECTURE's ultra-exceptional escalation, and UI/BROWSER's escalation are deliberately NOT `use` arrays - each is a separate single-candidate conditional rule, so Astra/Sol/Opus 5.5 can never be selected ahead of the primary by quota resolution. `openai-codex/gpt-6-sol` is the everyday cross-family route (RESEARCH's Pi-tooling rule, REVIEW's high-risk cross-family reviewer, ARCHITECTURE's exceptional peer, DEEP's diagnosis/ship escalations, TENTH-MAN's Claude-primary rule, and `firstmate/captain-startup-models.tsv`'s Captain-startup preference at medium effort); `openai-codex/gpt-6-astra` stays confined to Pi and to each category's own narrowest, most exceptional escalation - never a routine default. TENTH-MAN's rules route by the primary author's model family and, for Claude-authored work, by whether the Sol challenge already resolved the matter (Claude, unresolved after Sol -> Pi+Astra; Astra/OpenAI-codex -> OMP+Opus 5.5) as explicit, inspectable conditions rather than prose. Real semantic escalations remain separate same-category rules, and non-peer overrides stay prose-only. Preserve every category collision sentence and keep `tests/routing-taxonomy.sh` aligned with the exact candidate tuples.
- Bounded internal helpers remain supported by `firstmate/primary-policy.md` section 6: FirstMate owns macro orchestration; OMP's native `task` tool owns bounded task-local delegation. Pi has no bundled equivalent and stays not-applicable. `tests/worker-context.sh` provides `internal-prepare`/`internal-handoff` canaries inside the parent's worktree and `validate` report checks; corroborate reports with existing harness session evidence, not new telemetry. These checks do not enforce tool ordering or gate FirstMate completion; see README.md "Worker context and skill classes" and "Completion evidence limits".
- A checkpoint/ordering-gate experiment for target-discovery and a verification-provenance classifier were tried, then fully removed (see git history around "Remove abandoned provenance and checkpoint enforcement experiment"). `tests/worker-context.sh`'s `scope-prepare`/`scope-handoff`/`scope-validate` restore only the useful open-ended-discovery coverage from that removal (root-only launch scope, an independently selected nested candidate, body-only canary evidence that its instruction/skill were applied) - never read-order, tool-order, or completion-gate checks. Do not reintroduce that machinery.
- Adding or changing anything under `skills/*/SKILL.md` from a disposable task worktree makes `tests/smoke.sh`'s "every configured global skill is installed" check fail, for the same structural reason `install.sh` reports drift there: a worktree cannot symlink into the machine's shared `~/.agents/skills`. Expected there, not a regression - a real reconcile requires `./install.sh` (no `--verify`) from the primary checkout, never from a task worktree.
- `./install.sh --verify` is read-only and safe from a disposable worktree. Plain `./install.sh` repoints the live machine's launcher, skills, and dispatch symlinks at its checkout: run it only from the primary checkout, never a task worktree. Smoke's installer-drift failure against primary-checkout paths is expected from a worktree. Its live extension check uses the recorded Captain harness (`fm_omp_extension_owns_supervision` or the Pi equivalent); these checks inspect actual load state and can fluctuate with live-session timing, not code changes.
- `fm board` (`bin/fm-board`, `board/board.html`) is a lightweight persistent Kanban projection of live Firstmate work, not a competing task database. Current state lives at `$FM_HOME/data/board/state.json` (stable ids, never regenerated); `$FM_HOME/data/board/events.jsonl` is append-only debugging history that rendering never replays, and an unchanged projection is neither rewritten nor logged. `list`/`show`/`summary`/`render`/`open` deterministically reconcile from Firstmate's own authoritative state (`$FM_HOME/state/home-summary.json`, `bin/fm-crew-state.sh` in the official checkout) - never an LLM, never a daemon - classifying from structured fields only, never hold prose; README.md "Board columns" states the column rules and `bin/fm-board`'s `CREW_STATE_TO_BOARD`/`_queued_state` own them (a finished worker is `waiting_review`, only a landed backlog row is `done`; a live captain call is `waiting_review`, a dated/aged deferral is `todo`, an unresolved blocker id is `blocked`). Reconcile also retires (deletes) any `source: firstmate` row whose id no longer appears on any summary surface, because Firstmate's own retention (`tasks-axi done` pruning, the bounded `landed` window) forgets finished tasks quickly. Retirement requires provably complete surfaces (`_retirement_protected`): no `omitted` surface, and either `valid: true` or an inventory-mismatch-only invalidity (`terminal_in_flight`, `unowned_current`, `orphan_in_flight` with its ids protected, `child_current_unavailable`) - the live home routinely publishes `valid: false`/`terminal_in_flight` for days while a local-only task awaits approval, and gating on `valid: true` alone froze every stale card. `missing_backlog`/`unstructured_current`/truncated summaries retire nothing, and `source: manual` rows (`fm-board add`) are never retired. The page is a static `file://` snapshot: `open` re-renders while the viewer it launched runs (`cmd_open`), and the page re-reads `board-data.js` itself every few seconds, preserving the selected tab. CLI: `add/update/move/list/show/summary/render/open [--lavish]`; task ids are always explicit (`--id`), never generated. `home-summary.json`'s `landed` entries never carry `repo` (only `queued`/`active_children` do); `reconcile()` never lets that overwrite a project the id already carries on the board, and only for an id with no prior board project does it fall back to `FIRSTMATE_ROOT/bin/fm-tasks-axi.sh show <id>`'s `repo:` line. Tests: `tests/board.sh` (fixture-isolated `FM_HOME`, a fake `fm-crew-state.sh`/`home-summary.json` cover the lifecycle matrix, the retire-on-absence guards, idempotent reconcile, and manual-row preservation without touching the real machine home).
