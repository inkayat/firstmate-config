# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `README.md` is the project-level source of truth: layout, install, the multi-project Captain model, and routing. Read it first.
- The Captain's project-selection precedence ("which project", the launch-directory hint, and why a project's instructions/skills are never preloaded at startup) is owned by `firstmate/primary-policy.md` section 1; do not duplicate it here.
- The delegated-worker context/skill-class contract (why Pi and OMP need an explicit compact handoff instead of "the harness discovers project instructions natively", the three skill populations - official FirstMate internal, firstmate-config shared worker, project-local - and the required per-task path/precedence handoff) is owned by `firstmate/primary-policy.md` section 2 and README.md "Worker context and skill classes"; do not duplicate it here.
- Tests: `tests/smoke.sh` (launcher/install/herdr), `tests/captain-harness.sh` (OMP default, explicit Pi fallback, native availability and diagnostic agreement), `tests/model-selection.sh` (Pi fallback's original model chain), `tests/multi-project-captain.sh` (project resolution, real `bin/fm-spawn.sh` dispatch/isolation, instruction/skill separation, Pi/OMP routing - requires `tmux` and `treehouse` on `PATH`, uses an isolated `TMUX_TMPDIR` server so it never touches the shared/live session), `tests/doctor.sh` (`fm doctor` statuses/exit codes/JSON schema, fully fixture-isolated - see its header for the hermetic PATH rationale), `tests/stack-manifest.sh` (shared parser/comparator plus fixture-isolated install/doctor/version scenarios, offline local Git origins), `tests/worker-context.sh` (worker context handoff: offline fixture plus Pi native-loader probe, never a substitute for a live delegated Pi/OMP fixture run), `tests/vault.sh` (specialist skill vault: install.sh step 10 clone/pin/idempotency/offline, the immutable commit-qualified layout (new pin beside the old, prior commit byte-stable, no in-place re-pin, no leftover incomplete directory) and catalog verification, plus `fm doctor`'s `vault.pin`/`vault.no_global_leak` state coverage including a symlink-alias OMP registration and an unresolvable configured path, fully offline via a local git origin - never the vault's own selection/lookup behavior, which is that repository's own responsibility).
- `firstmate/stack-manifest.tsv` is the single tracked source of truth for stack compatibility (official FirstMate repo/validated commit, Pi/OMP/Herdr min/tested versions - see README.md "Stack compatibility" and the manifest's own header comment for what is deliberately excluded). `firstmate/fm-stack-manifest.sh` is the one parsing/comparison owner, sourced by `install.sh`, `bin/fm-doctor`, and `bin/fm-version`; never duplicate its TSV parsing or version comparison in a script or a test - fixtures may generate alternate manifests, but assertions against the real tracked manifest must load it dynamically (`stack_manifest_load`), never hardcode its values as separate literals.
- `data/projects.md`/`bin/fm-project-mode.sh` is a registered-**delivery-posture** lookup only, never a project resolver or location lookup (its own header, AGENTS.md section 7). Project name -> path resolution is `bin/fm-spawn.sh`'s own `projects/<name>` shorthand against `$FM_HOME/projects/<name>` - the one mechanism upstream provides; do not add a second one.
- `firstmate/fm-captain-lib.sh` owns Captain harness selection and availability, shared by `bin/fm`, `bin/fm-doctor`, and `bin/fm-version`; extend it rather than adding another detector. README.md's startup and "Captain startup model" sections own OMP-default / explicit-Pi behavior. OMP catalog diagnostics must retain `--no-extensions`: native `models` otherwise binds factories and can overwrite live FirstMate markers. Actual Captain startup uses native project discovery, never the worker overlay. Doctor's header owns its read-only mandatory-vs-advisory exit gate.
- `firstmate/crew-dispatch.json` routes work through eleven dispatch categories (QUICK, EXPLORE, RESEARCH, REVIEW, ARCHITECTURE, TENTH-MAN, IMPLEMENT, IMPLEMENT-LARGE, DEEP, UI/BROWSER, DEFAULT): twenty-two `rules` entries (ten distinct `category` values; EXPLORE, RESEARCH, IMPLEMENT-LARGE, REVIEW, ARCHITECTURE, TENTH-MAN, IMPLEMENT, and UI/BROWSER each span two or three more-specific rules sharing one category value; DEEP spans four single-candidate conditional rules - scout primary, scout Astra escalation, ship primary, ship Astra escalation) plus the untagged `default` catch-all for DEFAULT. FirstMate resolves a matched rule's `use` array through its quota-array procedure, so arrays hold only deliberate semantic peers: QUICK pairs Haiku/Luna, ARCHITECTURE's exceptional rule pairs Opus 5.5/Astra. DEEP and UI/BROWSER's escalations are deliberately NOT `use` arrays - each is a separate single-candidate conditional rule, so Astra/Opus 5.5 can never be selected ahead of the primary by quota resolution. TENTH-MAN's two rules route by the primary author's model family (Claude -> Pi+Astra, Astra/OpenAI-codex -> OMP+Opus 5.5) as explicit, inspectable conditions rather than prose. Real semantic escalations remain separate same-category rules, and non-peer overrides stay prose-only. Preserve every category collision sentence and keep `tests/routing-taxonomy.sh` aligned with the exact candidate tuples.
- Bounded internal helpers remain supported by `firstmate/primary-policy.md` section 6: FirstMate owns macro orchestration; OMP's native `task` tool owns bounded task-local delegation. Pi has no bundled equivalent and stays not-applicable. `tests/worker-context.sh` provides `internal-prepare`/`internal-handoff` canaries inside the parent's worktree and `validate` report checks; corroborate reports with existing harness session evidence, not new telemetry. These checks do not enforce tool ordering or gate FirstMate completion; see README.md "Worker context and skill classes" and "Completion evidence limits".
- A checkpoint/ordering-gate experiment for target-discovery and a verification-provenance classifier were tried, then fully removed (see git history around "Remove abandoned provenance and checkpoint enforcement experiment"). `tests/worker-context.sh`'s `scope-prepare`/`scope-handoff`/`scope-validate` restore only the useful open-ended-discovery coverage from that removal (root-only launch scope, an independently selected nested candidate, body-only canary evidence that its instruction/skill were applied) - never read-order, tool-order, or completion-gate checks. Do not reintroduce that machinery.
- Adding or changing anything under `skills/*/SKILL.md` from a disposable task worktree makes `tests/smoke.sh`'s "every configured global skill is installed" check fail, for the same structural reason `install.sh` reports drift there: a worktree cannot symlink into the machine's shared `~/.agents/skills`. Expected there, not a regression - a real reconcile requires `./install.sh` (no `--verify`) from the primary checkout, never from a task worktree.
- `./install.sh --verify` is read-only and safe from a disposable worktree. Plain `./install.sh` repoints the live machine's launcher, skills, and dispatch symlinks at its checkout: run it only from the primary checkout, never a task worktree. Smoke's installer-drift failure against primary-checkout paths is expected from a worktree. Its live extension check uses the recorded Captain harness (`fm_omp_extension_owns_supervision` or the Pi equivalent); these checks inspect actual load state and can fluctuate with live-session timing, not code changes.
- `fm board` (`bin/fm-board`, `board/board.html`) is a lightweight persistent Kanban projection of live Firstmate work, not a competing task database. Current state lives at `$FM_HOME/data/board/state.json` (stable ids, never regenerated); `$FM_HOME/data/board/events.jsonl` is append-only debugging history that rendering never replays. `list`/`show`/`summary`/`render`/`open` deterministically reconcile from Firstmate's own authoritative state (`$FM_HOME/state/home-summary.json`, `bin/fm-crew-state.sh` in the official checkout) - never an LLM, never a daemon. When that summary is a complete publication (`valid: true`, no `omitted` surfaces), reconcile also retires (deletes) any `source: firstmate` board row whose id no longer appears on any summary surface - Firstmate's own backlog/summary retention (`tasks-axi done` pruning, the bounded `landed` window) forgets finished tasks quickly, so an upsert-only reconcile would otherwise freeze their last-seen state forever; an invalid or truncated summary retires nothing, and `source: manual` rows (`fm-board add`) are never retired. The page is a static `file://` snapshot, so a browser refresh only re-reads the generated files; `open` keeps them current while the viewer it launched is running and stops when it exits (`bin/fm-board`'s `cmd_open` owns how); `bin/fm-board`'s own module docstring and its `CREW_STATE_TO_BOARD` table own the exact state-to-board lifecycle mapping (a worker's own `done` status always projects as board `waiting_review`; only a landed/archived backlog entry becomes board `done`, since only the captain's approval closes that loop). CLI: `add/update/move/list/show/summary/render/open [--lavish]`; task ids are always explicit (`--id`), never generated. `home-summary.json`'s `landed` entries never carry `repo` (only `queued`/`active_children`/`endpoints` do); `reconcile()`'s landed branch never lets that overwrite a project the id already carries on the board, and only for an id with no prior board project does it fall back to `FIRSTMATE_ROOT/bin/fm-tasks-axi.sh show <id>`'s `repo:` line - never for an id reconcile already knows. Tests: `tests/board.sh` (fixture-isolated `FM_HOME`, a fake `fm-crew-state.sh`/`home-summary.json` cover reconcile mapping, the retire-on-absence guard, and manual-row preservation without touching the real machine home).
- The optional specialist skill vault (`agent-skill-vault`, private) is pinned by exact commit in `skills/vault.lock` (format matches `skills/external.lock`: `<repo><TAB><40-hex-commit>`). `firstmate/fm-vault-lib.sh` is the one owner of that parsing, of the immutable commit-qualified cache path (`~/.local/share/firstmate-config/vault-src/<owner>-<repo>/<exact-commit>/`, separate from `skills-src/`) and of cache verification (clean detached checkout at that exact commit, `catalog.yaml` plus `bin/lookup.ts` present, and - where `bun` is installed - the vault's own lookup surface parsing its catalog); `install.sh` step 10, `bin/fm-doctor`, and `bin/fm-version` all go through it, never their own copy. A commit directory is created once (clone into a `.incomplete` staging directory, verified, then moved into place) and then only read: a new pin is a new directory, an existing one is never re-pinned, reset, or deleted, superseded commits are simply left alone (no cleanup job by design), and the only deletion is a failed clone removing its own staging directory. `install.sh` exports the verified directory as `FM_SKILL_VAULT_ROOT` via `~/.config/firstmate-config/env` (the old `FM_VAULT_ROOT` name is gone, not aliased), and publishes it only after that directory verifies: a run whose vault step fails keeps the previously published root if it still verifies and otherwise leaves the value empty, never a path to unverified vault content. `fm doctor`'s `vault.pin` (absent/wrong_revision/dirty/corrupt/catalog_missing/catalog_invalid/unverified_catalog/healthy) and `vault.no_global_leak` checks stay advisory, like `skills.global_installation`: they never change the exit code. `vault.no_global_leak` decides containment on canonical paths - it tilde-expands and resolves every filesystem path in OMP's own config, in both the block-list and flow-sequence (`key: ["/a"]`) YAML shapes, so a symlink alias into the cache is caught, keeps a verbatim cache-path `grep` as a lower-bound safety net, and reports UNKNOWN (never PASS) for a configured path it cannot resolve. `fm version`'s `specialist_skill_vault.pinned_commit` is a low-weight identity field, not a health check. Consumption (lookup via the vault's own `bin/lookup.ts --category`/`--id`, the shared skill budget and its no-self-expansion rule, project-local precedence, handoff format) is owned by `firstmate/primary-policy.md` "Specialist skill vault" - never duplicate it here. The vault's own `catalog.yaml`/`README.md` and `bun test` suite are the authority for its content, provenance, and selection safety; this repository only pins, caches, and reports on it.
