Architecture and startup

Two decisions are kept apart on purpose: which harness and model the Captain runs on, and which harness and model each worker gets. The first is on this page. The second is Dispatch routing.

The stack

fm
 └─ OMP Captain
     └─ FirstMate
         └─ Herdr
             ├─ Pi workers
             └─ OMP workers
PieceResponsibility
fmResolves paths, picks harness and model, and starts the Captain. It owns no lifecycle logic: the fleet lock, watcher, heartbeat, wake queue, spawn, and teardown all stay in the official checkout.
CaptainAn OMP session (or Pi, by explicit choice) that talks to you and delegates.
FirstMateTask lifecycle and delegation.
HerdrRuntime and sessions for the Captain and its workers.
WorkersPi or OMP sessions in isolated task worktrees, chosen by the routing table.

Choosing the Captain harness

OMP is the default. Pi is an explicit fallback and is never selected automatically:

fm                  # OMP Captain
fm --harness omp    # same, spelled out
fm --harness pi     # Pi Captain
fm --harness pi doctor

--harness goes before the subcommand and applies to doctor and version as well. Any other value is rejected with expected omp or pi. Overriding the harness executable is done with FM_OMP_BIN or FM_PI_BIN.

Where the Captain runs

The harness runs inside the official FirstMate checkout, not in the directory you launched from. FirstMate's AGENTS.md is a working-directory context file, and a Captain that never loaded it would not be a FirstMate Captain. Two consequences:

  • No project's AGENTS.md, CLAUDE.md, or project-local skills are preloaded as global authority. Each is resolved per task.
  • Launching from inside a project never binds the session to it. Your shell's directory is untouched.

The directory you launched from is passed on as FM_FORK_ORIGIN_CWD, with FM_FORK_ORIGIN_IS_PROJECT set to true only when it is itself a Git project. It is a hint for one task, never a lock.

Which project a task belongs to

Every delegated task names or implies exactly one project. The Captain resolves it per task, stopping at the first rule that answers:

  1. An explicit path or project name in your request.
  2. A name that matches an entry in FirstMate's registry, data/projects.md. No second project database or resolver is added.
  3. FM_FORK_ORIGIN_CWD as a default-project hint, only when it is a Git project.

If it is still ambiguous, the Captain asks one concise question. It does not guess silently. Concurrent tasks may target different projects, and each runs in its own isolated task worktree.

The startup model chain

firstmate/captain-startup-models.tsv is an ordered list of candidates, tab-separated as model, effort, and an optional harness. The launcher walks it top to bottom and takes the first candidate that is not known to be unavailable.

#ModelEffortHarness
1openai-codex/gpt-6.1-solmediumboth
2anthropic/claude-sonnet-5-5highOMP only
2pi-claude-code-provider/sonnethighPi only
3openai-codex/gpt-6-astraxhighboth

So an OMP Captain tries Sol 6.1, then Claude Sonnet 5.5, then Astra; a Pi Captain tries Sol 6.1, then the Claude Code provider's Sonnet alias, then Astra.

  • A row whose harness column does not match the active Captain harness is skipped entirely - never probed, never selected. An OMP Captain can never be launched with a Pi-only provider id.
  • Probing is non-billable. Only an authoritative UNAVAILABLE skips a candidate; AVAILABLE and UNKNOWN both stay eligible.
  • If nothing is eligible the launcher stops with no configured captain startup model is available and lists each candidate's reason.
  • When the chosen model is not the first one, the launcher prints a FirstMate Captain fallback: line with the reasons.

How availability is probed

HarnessProbe
OMPThe native catalog, omp models --json --no-extensions, run from the FirstMate checkout. A model absent from the catalog, or an unsupported effort, is UNAVAILABLE; an unreadable catalog is UNKNOWN. --no-extensions must stay, otherwise the call can overwrite live FirstMate markers.
PiPi's own model listing and auth check. The one exception is pi-claude-code-provider: Pi's auth check does not load extension providers and misreports it, so it is checked with the provider's zero-inference claude auth status instead.

"Available" means credentials resolve. Live validity and quota are not probed.

Two ids for the same family

OMP names Sonnet anthropic/claude-sonnet-5-5. Pi's chain step reaches it through the Claude Code provider as the unversioned alias sonnet, which Claude Code resolves to its own current Sonnet. The alias moves when the installed Claude Code does; nothing here changes. Pi also has a built-in, version-pinned anthropic/claude-sonnet-5-5 that uses Anthropic credentials configured in Pi; the chain does not use it, the claude preset below does.

The selected model and effort are passed to the harness as --model and --thinking, for this launch only.

Choosing a model for one launch

fm --model claude
fm --model claude --harness pi

--model, before or after --harness, takes one of two presets. Each resolves to the selected harness's own id for that model, with a fixed effort:

PresetOMPPiEffort
codexopenai-codex/gpt-6.1-solopenai-codex/gpt-6.1-solmedium
claudeanthropic/claude-sonnet-5-5anthropic/claude-sonnet-5-5high

Both ids are exact, version-pinned entries in OMP's native catalog and in Pi's built-in registry. Pi's pi-claude-code-provider/sonnet is an unversioned Claude Code alias and is never used for claude, so a Pi Captain needs Anthropic credentials configured in Pi for this preset.

The preset is checked by the same probe as the chain and used only when its exact model and effort are AVAILABLE. Any other value, an unavailable model, an unsupported effort, or an unverifiable catalog prints fm: warning: requested model ..., and the launcher walks the unchanged chain - default model and effort - on the same harness. A raw model id is never passed through, and nothing is persisted. A missing harness, Herdr, or an empty chain still stops the launch.

Extensions

The Captain needs FirstMate's primary watcher and turn-end guard extensions from the official checkout. fm --check and fm doctor fail if they are missing.

  • OMP discovers them from .omp/extensions in the checkout. The launcher passes no -e flags and no worker overlay.
  • Pi has two modes, chosen by FM_PI_EXTENSIONS: explicit (the launcher passes both extensions), discover, or auto (the default). auto uses discover when ~/.pi/agent/trust.json marks the FirstMate checkout as trusted, and explicit otherwise.

Environment the Captain receives

  • FM_HOME, FM_BACKEND, FM_CONFIG_ROOT, and the two FM_FORK_ORIGIN_* variables are exported.
  • Harness identity markers that leak from the shell you launched in (CLAUDECODE, OMPCODE, PI_CODING_AGENT, FM_PI_HARNESS, FM_OMP_HARNESS, CURSOR_AGENT, CURSOR_INVOKED_AS, GEMINI_CLI, GROK_AGENT, and the removed FM_SKILL_VAULT_ROOT) are cleared, so a Captain started from another agent's pane does not misreport its own harness. Herdr pane identity is kept on purpose.
  • The launcher writes $FM_HOME/state/.fm-launch: a record of what this Captain was actually started with. Nothing reads it to make a decision; it exists so you can confirm the launch afterwards.

Captain preferences

install.sh seeds $FM_HOME/data/captain.md once from firstmate/captain.md and never overwrites it. The template tells the Captain to read firstmate/primary-policy.md at session start and sets a working style: evidence over reassurance, short answers, and ask before anything destructive outside a task worktree. Edit your machine's copy freely; it survives every update.
