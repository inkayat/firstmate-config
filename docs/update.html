Update and recovery

fm update follows the verified FirstMate fork's explicit inkayat-main branch, then updates firstmate-config and reconciles the machine. Official upstream is integrated separately, never automatically.

Run an update

fm update

fm update --check instead checks local guards and prints source/branch/target/pin without fetching, updating or installing. It cannot prove remote freshness. Normal update, in order:

  1. Check both checkouts first. Inspect local guards, require the manifest's exact distribution origin and explicit branch, then fetch that branch and the config remote. Each checkout must equal, or be a plain fast-forward behind, its upstream.
  2. Fast-forward the FirstMate distribution checkout (FIRSTMATE_ROOT) with git merge --ff-only origin/inkayat-main.
  3. Fast-forward the firstmate-config checkout to its upstream.
  4. Reconcile. Run that checkout's own ./install.sh, then ./install.sh --verify. The run only counts as complete if verify reports 0 drift item(s), 0 failure(s).

On success the last lines name what happened:

Checking FirstMate distribution (https://github.com/inkayat/firstmate.git, branch inkayat-main)...
Fetching FirstMate distribution origin/inkayat-main...
Fetching firstmate-config origin...
Updated FirstMate distribution inkayat-main: a1b2c3d -> e4f5a6b (3 commits from origin/inkayat-main)
...
Reconciling machine state (updated to 9c8d7e6)...
...
fm update complete: FirstMate distribution a1b2c3d -> e4f5a6b; firstmate-config 5c9252f -> 9c8d7e6; machine reconciled and verified.
A running Captain keeps the instructions it loaded at startup and was not restarted or notified.
To adopt the update later, end the Captain session, then run fm again.
Secondmates and projects were not updated.

Already-current checkouts are reported; normal update still reconciles and verifies. Check-only never runs those steps.

A running Captain keeps what it already loaded

A running Captain keeps the instructions, skills, and launch-time wiring it already loaded. To adopt an update, end the Captain session and run fm again. Files a running session reads afterwards are the updated ones: a Pi session whose own Ponytail mode is lite, full or ultra injects the new Ponytail prompt on its next turn, although the default stays off.

What it never does

  • Force, stash, reset, merge, rebase, discard, or push anything.
  • Delete a branch or file. The only pruning is git fetch --prune of stale remote-tracking refs in the firstmate-config checkout.
  • Update secondmates or projects.
  • Restart or notify a running Captain.

Refusals

These stop the run in step 1; neither working tree changes. Distribution checkout refusals end with nothing was changed.

ConditionWhat to do
FIRSTMATE_ROOT is missing, is not the root of a Git checkout, or has no AGENTS.mdPoint FIRSTMATE_ROOT at the real checkout, or run ./install.sh to clone it.
Distribution origin differs from manifest firstmate_repo, including an insteadOf rewritePreserve existing remotes and work, then deliberately configure the verified fork. No automatic official fallback.
Detached/wrong branch, wrong tracking, or local origin/HEAD is not origin/inkayat-mainFollow migration below; GitHub's fork default main is not the distribution branch. Never use git remote set-head origin -a.
Uncommitted/untracked changes or unfinished Git operationPreserve and resolve them manually; never reset or discard to bypass the guard.
Local commits missing from origin/inkayat-main, or divergencePreserve that work on its existing branch; integrate deliberately, not through update.
firstmate-config checkout is dirtyCommit or stash it yourself, then re-run. The command lists the dirty paths first.
firstmate-config checkout is detachedCheck out a branch (normally main).
firstmate-config branch has diverged from its upstreamResolve the divergence manually.
firstmate-config branch has no upstream, or the fetch failsSet one with git branch -u origin/<branch>, or fix connectivity.

Partial updates

Step 2 can succeed and a later step can still fail. There is no multi-repository rollback, so that state is reported honestly instead of as success:

fm-update: install.sh failed after update; repository is at 9c8d7e6 but machine state was not reconciled
fm-update: PARTIAL UPDATE: FirstMate distribution was fast-forwarded (a1b2c3d -> e4f5a6b), but the firstmate-config update did not complete; fix the error above and re-run fm update

The exit status is nonzero. Recovery is the same each time:

  1. Read the error above the PARTIAL UPDATE line. It comes from the failing step: the fast-forward, install.sh, or install.sh --verify.
  2. Fix that cause - a missing tool, a link location that is not ours, a dirty checkout.
  3. Re-run fm update. Already-applied fast-forwards are reported as up to date and the reconcile runs again.
  4. Only a run that ends with fm update complete updated everything.

To inspect installed state without pulling, run ./install.sh --verify (read-only) or fm doctor from the primary checkout.

Ahead of the validated baseline

This configuration records its validated fork commit in firstmate/stack-manifest.tsv. Once the distribution checkout moves past it, fm doctor and install.sh report it as ahead (WARNING, not drift) until the manifest is moved by a reviewed change. A checkout behind the baseline, or diverged from it, is a FAIL in fm doctor.

One-time updater transition / Omarchy

Preparation candidate, not yet published. Replace APPROVED_FULL_CONFIG_COMMIT below only with the separately reviewed and published full config commit containing this bootstrap support. The older d7e3fc7 does not contain this follow-up; do not substitute a moving main script URL. Linux/Omarchy execution is unverified; no machine transition or session restart was performed during preparation.

The old installed updater validates official origin before fetching config. On the known fork-origin/local-main layout it therefore cannot download its own replacement. A clean official-origin installation can fetch new config, but that success alone does not switch the core source. Use this one-time command for either layout; after it completes, ordinary fm update is sufficient.

Trust boundary: this obtains code only from the verified owned repository https://github.com/inkayat/firstmate-config.git, checks a full approved revision is on its origin/main, checks out that exact revision, and pauses for inspection before execution. A commit hash verifies identity, not trust: obtain the approved hash through the reviewed publication handoff. No curl-pipe-shell, downloaded instructions evaluated as shell, sudo, daemon or new dependency. The temporary checkout is retained for inspection, never installed or linked.

bash -eu -c '
revision=$1
config=$2
[[ $revision =~ ^[0-9a-f]{40}$ ]] || { echo "Supply the approved full config commit, not a placeholder or branch" >&2; exit 1; }
repo=https://github.com/inkayat/firstmate-config.git
stage=$(mktemp -d "${TMPDIR:-/tmp}/fm-bootstrap.XXXXXX")
printf "Inspectable bootstrap source retained at %s\n" "$stage"
git -C "$stage" init -q
git -C "$stage" remote add origin "$repo"
[ "$(git -C "$stage" remote get-url origin)" = "$repo" ] || { echo "Refusing rewritten source URL" >&2; exit 1; }
git -C "$stage" fetch --quiet --no-tags origin refs/heads/main:refs/remotes/origin/main
git -C "$stage" cat-file -e "$revision^{commit}"
git -C "$stage" merge-base --is-ancestor "$revision" origin/main
git -C "$stage" checkout --quiet --detach "$revision"
git -C "$stage" --no-pager log -1 --format=fuller
printf "Inspect %s (updater, migration helper, manifest and installer); then type the full approved commit to execute: " "$stage"
read -r approval
[ "$approval" = "$revision" ] || { echo "Not approved; no installed checkout changed" >&2; exit 1; }
bash "$stage/bin/fm-update" --bootstrap "$config"
' bootstrap APPROVED_FULL_CONFIG_COMMIT /absolute/path/to/persistent/firstmate-config

The command resolves FIRSTMATE_ROOT through the existing machine env file, as normal update does. Check that file first; for nondefault installations provide the correct existing FM_CONFIG_ENV. The final argument must be the persistent installed config Git root, not the temporary checkout. Existing authenticated toolchain and network access are prerequisites; git, pi, omp, and herdr must already be on PATH. No runtime is launched. If the new updater is already installed, fm update --migrate is the same opt-in legacy adoption path without downloading a bootstrap checkout.

Accepted layouts and refusals

Both persistent checkouts and the bootstrap source must be clean physical Git roots with no unfinished operation. Migration also refuses ignored untracked content conservatively: preserve it outside the checkout yourself before retrying. Config must be on main, track the exact owned origin/main, and fast-forward to the inspected bootstrap revision; a newer config needs a reviewed newer bootstrap, never a downgrade. The fork branch must contain the manifest pin e73653772c7bf7329e58d6425ad74752b5b2b8bf.

  • Clean official-origin main: retain official as upstream, add/select fork origin, preserve the old main tip, create or safely fast-forward inkayat-main.
  • Known fork-origin local main: preserve its tip and other remotes, retain/add exact official upstream, switch to the safe fork branch. The generic skill-preparation fix must already be published there; no local-only work is adopted.
  • Already migrated fork/branch/tracking: safe repeat; still reconcile and verify.
  • Dirty/untracked/ignored content, local-only/diverged work, unknown origins, conflicting upstream or target branch/tracking, rewritten URLs, explicit custom push URLs, detached or unexpected branches, missing tools and unfinished operations: refuse before changing either working tree or remote settings. Fetches may already have moved tracking refs/FETCH_HEAD; never fetch or merge official automatically.

All existing branches and unrelated remote connections are retained. No force/reset/stash/discard/history rewrite. Migration sets local origin/HEAD=origin/inkayat-main, not GitHub’s default main. It fast-forwards config to the inspected revision, then uses the existing installer/reconciliation/verification owner, including conservative workflow-link retirement and preservation of user-owned ordinary files, roles, bots and both skill paths. Fresh installs remain pinned clones; ordinary install.sh still never migrates an existing source.

Not atomic: interruption or a later config/install failure reports PARTIAL MIGRATION, completed progress and both HEADs; no rollback or success is claimed. Inspect both repositories, resolve the stated failure and repeat the same command. Official-origin adoption adds/verifies upstream before changing the existing origin URL; it never removes origin. Existing official branch connections and missing cached tracking refs are preserved under upstream without overwriting existing upstream refs, while the selected distribution branch retains origin tracking. Each intermediate remote-adoption layout is already retryable; unrelated missing/custom origins still refuse. Keep source checkouts quiescent during adoption. Running Captains are never restarted or notified; already loaded policy remains unchanged. Fresh installations use the normal installer directly, with no bootstrap step.

fm update --check   # source/branch/local guards; not migration proof by itself
fm version
fm doctor
fm update           # subsequent maintenance: fork inkayat-main + config, reconcile, verify

Official updates: explicit human integration

In a separate clean integration checkout, keep origin=https://github.com/inkayat/firstmate.git and upstream=https://github.com/kunchenguid/firstmate.git. Fetch origin/inkayat-main and upstream/main, create a new integration branch from the fork branch, then explicitly merge upstream/main. Resolve conflicts while retaining the generic preparation fix; run relevant tests, inspect the complete diff, and publish the approved fast-forward to origin/inkayat-main only. Never push to official. Move the manifest pin only after that exact commit has been validated. Normal machine updates consume that fork branch; they never perform this integration.

Updating a pinned dependency

Shared skills from other repositories are pinned by commit in skills/external.lock; fm update never moves a pin. For the Ponytail skills there is a dedicated helper:

ponytail-update
git diff -- skills/external.lock

ponytail-update requires a clean main that can fast-forward with origin/main. It checks the latest stable Ponytail release; if one is newer it rewrites the pin, runs the Ponytail test suites, applies it with ./install.sh, verifies, and checks again. It does not commit, merge, push, create branches, or tag. Review the diff and commit it through your normal workflow; other machines then converge with fm update.
