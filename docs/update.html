Update and recovery

fm update moves the official FirstMate checkout and this repository to their remote tips, then reconciles the machine. It only ever fast-forwards, and it refuses anything else without changing a file.

Run an update

fm update

It takes no options. In order:

  1. Check both checkouts first. Local state is inspected before any network call. Then the official default branch is resolved and both remotes are fetched - only remote-tracking refs move. Each checkout must equal, or be a plain fast-forward behind, its upstream.
  2. Fast-forward the official FirstMate checkout (FIRSTMATE_ROOT) with git merge --ff-only.
  3. Fast-forward the firstmate-config checkout to its upstream.
  4. Reconcile. Run that checkout's own ./install.sh, then ./install.sh --verify. The run only counts as complete if verify reports 0 drift item(s), 0 failure(s).

On success the last lines name what happened:

Checking default branch of official FirstMate (https://github.com/kunchenguid/firstmate.git)...
Fetching official FirstMate origin...
Fetching firstmate-config origin...
Updated official FirstMate main: a1b2c3d -> e4f5a6b (3 commits from origin/main)
...
Reconciling machine state (updated to 9c8d7e6)...
...
fm update complete: official FirstMate a1b2c3d -> e4f5a6b; firstmate-config 5c9252f -> 9c8d7e6; machine reconciled and verified.
A running Captain keeps the instructions it loaded at startup and was not restarted or notified.
To adopt the official update, restart it through the official procedure: end the Captain session, then run fm again.
Secondmates and projects were not updated.

When both checkouts are already current you get Official FirstMate already up to date and Already up to date lines, and the reconcile and verify steps still run. A separate manual ./install.sh is not needed after a successful update.

The Captain does not hot-reload

A running Captain keeps the instructions, skills, and launch-time wiring it loaded. To adopt an update, end the Captain session and run fm again.

What it never does

  • Force, stash, reset, merge, rebase, discard, or push anything.
  • Delete a branch or file. The only pruning is git fetch --prune of stale remote-tracking refs in the firstmate-config checkout.
  • Update secondmates or projects.
  • Restart or notify a running Captain.

Refusals

These stop the run in step 1. Neither working tree has changed when you see them. Refusals about the official checkout end with nothing was changed.

ConditionWhat to do
FIRSTMATE_ROOT is missing, is not the root of a Git checkout, or has no AGENTS.mdPoint FIRSTMATE_ROOT at the real checkout, or run ./install.sh to clone it.
Official origin is not exactly the firstmate_repo value in stack-manifest.tsv, including an insteadOf rewriteFix the remote or the rewrite. The URL is checked on purpose so an update cannot pull from an unexpected place.
Official checkout is detached, on a branch other than origin's default, or the branch does not track origin/<default>Check out the default branch, or set tracking with git -C <FIRSTMATE_ROOT> branch -u origin/<default>.
Official checkout has uncommitted or untracked changes, or an unfinished merge, rebase, cherry-pick, revert, or bisectResolve or remove them yourself, then re-run.
Official checkout has local commits that are not on origin/<default>, or has divergedThat is unlanded work. Land it or move it to a branch, then re-run.
firstmate-config checkout is dirtyCommit or stash it yourself, then re-run. The command lists the dirty paths first.
firstmate-config checkout is detachedCheck out a branch (normally main).

firstmate-config branch has no upstream, or the fetch failsSet one with git branch -u origin/<branch>, or fix connectivity.

Partial updates

Step 2 can succeed and a later step can still fail. There is no multi-repository rollback, so that state is reported honestly instead of as success:

fm-update: install.sh failed after update; repository is at 9c8d7e6 but machine state was not reconciled
fm-update: PARTIAL UPDATE: official FirstMate was fast-forwarded (a1b2c3d -> e4f5a6b), but the firstmate-config update did not complete; fix the error above and re-run fm update

The exit status is nonzero. Recovery is the same each time:

  1. Read the error above the PARTIAL UPDATE line. It comes from the failing step: the fast-forward, install.sh, or install.sh --verify.
  2. Fix that cause - a missing tool, a link location that is not ours, a dirty checkout.
  3. Re-run fm update. Already-applied fast-forwards are reported as up to date and the reconcile runs again.
  4. Only a run that ends with fm update complete updated everything.

To inspect installed state without pulling, run ./install.sh --verify (read-only) or fm doctor from the primary checkout.

Ahead of the validated baseline

This configuration records the official FirstMate commit it was validated against in firstmate/stack-manifest.tsv. Once the official checkout moves past it, fm doctor and install.sh report it as ahead (WARNING, not drift) until the manifest is moved by a reviewed change. A checkout behind the baseline, or diverged from it, is a FAIL in fm doctor.

Updating a pinned dependency

Shared skills from other repositories are pinned by commit in skills/external.lock; fm update never moves a pin. For the Ponytail skills there is a dedicated helper:

ponytail-update
git diff -- skills/external.lock

ponytail-update requires a clean main that can fast-forward with origin/main. It checks the latest stable Ponytail release; if one is newer it rewrites the pin, runs the Ponytail test suites, applies it with ./install.sh, verifies, and checks again. It does not commit, merge, push, create branches, or tag. Review the diff and commit it through your normal workflow; other machines then converge with fm update.
