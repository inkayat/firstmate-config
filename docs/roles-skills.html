Roles and skills

A project's own AGENTS.md and CLAUDE.md always win. Shared skills and roles add expertise underneath them; they never override a project rule.

Precedence

project-native instructions
  > project-local skills
    > role / task policy
      > shared worker skills

A later tier never overrides an earlier one. Where a shared skill and a project rule disagree, the project wins, and the Captain spends one sentence in the brief saying so, so the worker does not rediscover the conflict.

How a project's instructions are resolved

Resolved per task, in this order, stopping at the first rule that answers:

  1. A precedence or resolution rule the project documents for itself.
  2. A more specific subtree over a broader one: the nearest instruction file to the code being changed wins.
  3. Within one scope: AGENTS.override.md, then AGENTS.md, then CLAUDE.md.
  4. Project-local skills: .claude/skills, .agents/skills, .agent/skills.

If two top-tier project rules genuinely contradict each other and nothing resolves it, the Captain stops and asks.

Roles

A role describes how to work and never outranks the project. There are eleven, at roles/<name>/ROLE.md. Each file opens with OMP task-agent frontmatter - name: fm-<name>, a description, and optional autoloadSkills, tools, and model - so the same file is the role a brief points at and an OMP agent definition. install.sh links each into ~/.omp/agent/agents/fm-<name>.md without replacing a foreign entry. A role pointer or tool list is not proof of native adoption or a runtime access restriction.

The dispatch category picks harness, model, and effort independently. Outside the two fixed category/role bindings, FirstMate inspects available role contracts and automatically chooses the narrowest fit for the whole authorized deliverable, including mutation and validation. Explicit compatible task choices win. No specialist-versus-normal question, automatic split or model change follows from selecting a role.

A role's autoloadSkills are default selections within the task budget and displaced by same-ground project-local skills. Native OMP agent use supports autoloading; FirstMate macro workers still need the explicit role/context/skill handoff below. Neither frontmatter nor fixture success proves genuine native defaults were applied. fm doctor checks managed defaults and frontmatter compatibility.

Skills are installed as symlinks. The pinned repositories are cloned once into a machine-local cache, and the addyosmani skills' relative links to shared references are satisfied by an extra ~/.agents/references link.

The documentation skill uses the existing exact addy pin in skills/external.lock, without a repository/schema/version bump. Its retained checkout carries the MIT copyright and permission notice; copies or substantial portions must preserve those obligations.

How skills are selected

Skills load on demand and are selected, not dumped. Per task the Captain picks at most two workflow or methodology skills and at most one reference skill, fewer by preference, and none when the task does not need one.

  • Before choosing, the Captain lists ~/.agents/skills and reads the relevant SKILL.md files directly. A recursive **/SKILL.md search is not enough, because symlinked skill directories can be skipped by glob traversal.
  • Choosing no skill requires a task-specific reason in the brief, not a generic "none needed". The chat display remains just Skills: none.
  • A project-local skill always wins over a shared one on the same ground.

Defaults, transitive methods and mandatory companions are not hidden outside this budget. For example, TDD replaces an optional verification/UI method rather than adding a third; writing-good-tests.md takes the one reference slot when required. Verification and real-client obligations still hold when their skill is not selected. Conditional accessibility/security/performance companions compete for that same reference slot; name any unmet companion under primary policy and do not claim the full method was applied when its required companion was not read and applied.

What a worker is told

"The harness discovers project instructions natively" is not enough: Pi and OMP differ in their search roots, override support, and skill precedence. So each delegated task carries an explicit, compact handoff, resolved against the worker's own isolated worktree:

  1. The selected project and subtree.
  2. The applicable instruction paths, relative to the worktree root, and which one wins at each scope.
  3. Each required project-local skill as a bare, worktree-relative path with a read-and-apply requirement.
  4. Each selected shared skill by name, with a read-and-apply requirement - never a pasted body.
  5. A pre-work check that pwd -P equals git rev-parse --show-toplevel, then reading every named path and reporting any that is missing or conflicting. Each selected skill, and any companion file it makes mandatory for the task (named by its absolute or ~/ path as its own entry), is read in full with the harness's own read tool before the first edit and before any shell work, continuing truncated output.
  6. A reminder to repeat steps 1-4 when the work moves into a new subtree.
  7. The assigned role and absolute role source path, input/output artifacts, actual worker identity distinct from any native agent identifier, acceptance, scope/mutation/validation boundaries, real dependencies and delivery/stop rule.
Guidance, not a gate

This is a handoff contract. It does not prove read order, skill application, or completion, and no configured runner enforces it. Worker reports can describe discovery; they cannot independently prove it.

The temporary routing, agent and skill trace

During the current debugging period the Captain prints one short block per actually assigned worker/stage. Never instantiate actors merely to display every stage:

Routing: <CATEGORY> [#n] | role <role> | <harness> | <provider/model> | <effort> | why: <reason>
Agent: <assigned role name>
Skills: <selected name>, <selected name>

Agent names only the assigned role, for example senior-fullstack. Skills lists only selected names, comma-separated: the skill directory name for SKILL.md and companion filename without .md. Skills: none stands alone. Paths, worker/native identity, authority, current stage and task-specific reasons stay in the instructions/handoff; Routing still shows the actual model/effort/category.

It discloses decisions already made; it is not reasoning, and it is never written to a file or into the brief. Selecting an instruction or skill does not prove reading or application. Workers still read and apply assigned context and methods, run actual checks, and report observed outcomes and limits under the ordinary handoff/completion policy.

tests/routing-trace.sh check compares a captured block with the actual spawn axes, matched rule and selected skill names. Agent must agree with Routing's role; optional trailing --brief <delivered-brief> compares it with Assigned role:. Missing or conflicting names fail agreement. The diagnostic cannot certify hidden paths, native adoption, application, outcome correctness or category choice.

When debugging ends, remove section 0's temporary diagnostic and matching guide references. Retain ordinary role selection and task handoff. This is not a completion gate or proof of installation.

Add or change a shared skill

A skill owned by this repository

Create skills/<name>/SKILL.md with name and description frontmatter. install.sh links every directory under skills/ that contains a SKILL.md.

A skill from another repository

Add a tab-separated line to skills/external.lock:

# <our-id>  <repo>  <commit>  <path-in-repo>  <installed-skill-name>

Always pin a full commit hash, never a branch: an unpinned global skill changes behavior on every project on the machine without a diff. To move a pin, change the hash, run ./install.sh, and commit. For Ponytail, ponytail-update does this for you; see Update and recovery.

Then confirm with ./install.sh --verify and fm doctor (the skills.global_installation check reports how many expected skills are installed).
