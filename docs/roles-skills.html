Roles and skills

A project's own AGENTS.md and CLAUDE.md always win. Shared skills and roles add expertise underneath them; they never override a project rule.

Precedence

project-native instructions
  > project-local skills
    > role / task policy
      > shared worker skills

A later tier never overrides an earlier one. Where a shared skill and a project rule disagree, the project wins, and the Captain spends one sentence in the brief saying so, so the worker does not rediscover the conflict.

How a project's instructions are resolved

Resolved per task, in this order, stopping at the first rule that answers:

  1. A precedence or resolution rule the project documents for itself.
  2. A more specific subtree over a broader one: the nearest instruction file to the code being changed wins.
  3. Within one scope: AGENTS.override.md, then AGENTS.md, then CLAUDE.md.
  4. Project-local skills: .claude/skills, .agents/skills, .agent/skills.

If two top-tier project rules genuinely contradict each other and nothing resolves it, the Captain stops and asks.

Roles

A role describes how to work and never outranks the project. There are twelve, at roles/<name>/ROLE.md. Each file opens with OMP task-agent frontmatter - name: fm-<name>, a description, and optional autoloadSkills, tools, spawns, and model - so the same file is the role a brief points at and an OMP agent. install.sh links each one into ~/.omp/agent/agents/fm-<name>.md, so every OMP session can spawn fm-<name>; an entry there that it did not create is left alone.

The dispatch category picks harness, model, and effort. It never picks a role, and a strong model never implies a special role. Outside ARCHITECTURE and TENTH-MAN a task may use a specialist role when its work shape matches; the category and rule are chosen first and never change because of it.

A role's autoloadSkills are its default skill selection, still inside the per-task budget below and still displaced by a project-local skill on the same ground. OMP injects them before a spawned agent's first prompt. fm doctor reports a default skill this repository does not manage and a role file whose frontmatter OMP would reject.

Team mode

Opt-in: a task runs as a team only when its brief names the team-lead role. The lead is an OMP worker (never Pi) that runs the task as a small team of OMP subagents inside its own worktree. It may spawn only the agents its spawns list names; OMP refuses any other with Cannot spawn.

Team roleDoes
team-leadRuns the phases below, owns integration, the rework loop, and the result. Never relabels a scope question.
product-ownerRequirements with acceptance criteria, the work split, stated assumptions, and open questions labeled scope or technical that it does not decide. Read-only.
backend-contractThe endpoint contract inside the technical plan's API boundaries, before implementation. Read-only.
qaAfter integration, runs the tests and exercises each changed flow end to end; reports pass or fail with evidence and never fixes code.
  1. Requirements. product-owner. Any scope question stops the task with needs-decision; a technical one the lead may resolve with cited evidence and a recorded condition that would reopen it.
  2. Technical plan. architecture writes the plan and API boundaries.
  3. Contract. backend-contract writes the endpoint contract when the plan has an API seam.
  4. Implementation. Implementers start together, in parallel: django-pro for a Django backend, frontend-master for web UI, senior-fullstack otherwise. Each reads the plan and contract before its first edit and touches only its owned paths.
  5. Integration, QA, review. The lead integrates and runs the tests, then a fresh qa, then - only after QA passes - a fresh code-reviewer.
  6. Rework. Each failure goes to the member who owns the path, for at most two rounds across QA and review; a third failure is needs-decision. The lead commits nothing unless its brief allows it.
Not a merge gate

The in-team review does not replace the independent review before merge. The planning members and the reviewer are read-only; members report to the lead, and only the lead reports to FirstMate.

Team profiles

Optional: a team task can carry a profile, teams/<name>.json, that configures who is on the team, what each member may write and whom it may message, and which operations the team may only request. fm team validate judges it against the real role frontmatter, so a profile only narrows what the global roles already allow; no role file is ever rewritten for one task. teams/web-feature.json is a proposed example, not a selected team.

  1. Bind at intake. The Captain runs fm team bind TASK --profile NAME --base COMMIT and writes a Team profile: NAME line in the brief. The task keeps its own snapshot under $FM_HOME/data/team-bindings/.
  2. Apply in OMP. install.sh links extensions/fm-team-policy.ts into OMP's user extension root. It acts only in the bound task's sessions; a bound task whose binding or snapshot is missing, corrupt, or tampered refuses everything but reads.
  3. Check before a relaunch. fm team check TASK re-validates the snapshot against the current roles.
  4. Audit at delivery. fm team audit TASK lists every committed, staged, unstaged, untracked, deleted, and renamed path and refuses anything outside the team scope.

Member and helper reads through OMP's tools stay inside the worktree and the shared skill and reference links that install.sh creates. Of internal URLs they read only local://, artifact://, agent://, rule://, and omp://; skill://, history://, credential-using schemes such as ssh://, and unknown schemes are refused. The lead reads as before.

Where it stops

These are in-process tool checks, not an OS boundary. bash can still write any file, read anything, and use every credential the user account holds, so read confinement binds only members without it. The lead is not confined and shares its session with members, rules loaded at startup never pass a tool call, and an https_read grant is an egress channel for everything its member can read; web_search stays available either way. The ops command patterns are best effort. The binding is writable by the same user, so its sha256 is a consistency check, not authorization. The audit proves the team's final-tree scope, not which member wrote what. The extension's decisions are tested against synthetic OMP hook events; a live OMP team session loading it has not been exercised yet.

How skills are selected

Skills load on demand and are selected, not dumped. Per task the Captain picks at most two workflow or methodology skills and at most one reference skill, fewer by preference, and none when the task does not need one.

  • Before choosing, the Captain lists ~/.agents/skills and reads the relevant SKILL.md files directly. A recursive **/SKILL.md search is not enough, because symlinked skill directories can be skipped by glob traversal.
  • Choosing no skill requires a task-specific reason, not a generic "none needed".
  • A project-local skill always wins over a shared one on the same ground.

What a worker is told

"The harness discovers project instructions natively" is not enough: Pi and OMP differ in their search roots, override support, and skill precedence. So each delegated task carries an explicit, compact handoff, resolved against the worker's own isolated worktree:

  1. The selected project and subtree.
  2. The applicable instruction paths, relative to the worktree root, and which one wins at each scope.
  3. Each required project-local skill as a bare, worktree-relative path with a read-and-apply requirement.
  4. Each selected shared skill by name, with a read-and-apply requirement - never a pasted body.
  5. A pre-work check that pwd -P equals git rev-parse --show-toplevel, then reading every named path and reporting any that is missing or conflicting.
  6. A reminder to repeat steps 1-4 when the work moves into a new subtree.
Guidance, not a gate

This is a handoff contract. It does not prove read order, skill application, or completion, and no configured runner enforces it. Worker reports can describe discovery; they cannot independently prove it.

The routing and skill trace

During the current debugging period the Captain prints a short block in chat before each delegation, and one after each worker finishes:

Routing: <CATEGORY> [#n] | role <role> | <harness> | <provider/model> | <effort> | why: <reason>
Skills: <skill> - <reason>; <skill> - <reason>

Skill evidence:
- <skill>: <observation citing `verbatim excerpt`>

It discloses decisions already made; it is not reasoning, and it is never written to a file or into the brief. tests/routing-trace.sh check compares a captured block with the real spawn and transcript, but a citation match is lexical only: it cannot prove the category was right or that a skill was applied.

Add or change a shared skill

A skill owned by this repository

Create skills/<name>/SKILL.md with name and description frontmatter. install.sh links every directory under skills/ that contains a SKILL.md.

A skill from another repository

Add a tab-separated line to skills/external.lock:

# <our-id>  <repo>  <commit>  <path-in-repo>  <installed-skill-name>

Always pin a full commit hash, never a branch: an unpinned global skill changes behavior on every project on the machine without a diff. To move a pin, change the hash, run ./install.sh, and commit. For Ponytail, ponytail-update does this for you; see Update and recovery.

Then confirm with ./install.sh --verify and fm doctor (the skills.global_installation check reports how many expected skills are installed).
