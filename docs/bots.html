Bots

A bot runs one role against one project on a daily window, an elapsed interval, or a selected remote-branch change. It is a spec file plus one watcher check, never a process: every admitted run is an ordinary FirstMate task.

New modes skip unfinished work; they do not terminate it

Interval and remote-branch bots share atomic skip-if-unfinished admission and a conservative minimum two-hour spacing bound. Their 1..60-minute wall-clock target is advisory, not a hard one-hour cap or provider-cancellation mechanism. Existing daily behavior is unchanged. See Trigger semantics and limits.

What a bot is

Each bot is a spec at $FM_HOME/data/bots/<name>.md, machine-local and never tracked. bin/fm-bot (fm bot) is its only writer and validates every field. A spec carries the whole routine:

FieldRule
roleAn existing roles/<role>/ROLE.md; a missing role is refused, never substituted.
projectThe registered project name.
routeAn existing CATEGORY #N rule in firstmate/crew-dispatch.json. create records that rule's harness, model, and effort (route_use); if the rule at that position later changes, the bot is reported invalid (route-changed) instead of silently re-targeted. Recreate it to accept the new rule. A spec without route_use is refused (route-unpinned), never routed by position.
scheduleDaily: daily or listed weekdays, with a same-day Europe/Stockholm --at/--until window of at least ten minutes; 02:xx is refused because of DST. Alternatively choose --every-hours N (whole hours, minimum two), or --on-remote NAME --on-branch BRANCH; never combine schedule modes. The one-shot watcher must be re-armed by the Captain; no mode launches a missed-occurrence backlog.
scopeOne line: what the bot looks at and what it produces.
limitsAdvisory wall-clock minutes per run (1..60 for new modes); optional candidate, file, and line caps and excluded paths. This field does not terminate a worker.
access, notifynone or a secret:<reference> name (never a secret); report or needs-decision-on-high.
levellocal-proposal (default), local-commit, or push; see Permission levels.

Create and inspect

Ask the Captain - "bot oluştur", "create a bot". The bot-builder skill collects the routine and the level in one batch, refuses missing pieces, and writes the spec only through fm bot create. It never invents authorization words, never picks a higher level than you asked for, and never activates or dispatches anything.

The /bots slash command is read-only: it runs fm bot list, or fm bot show <name> when you name a bot, and prints name, state, level, role, project, schedule, expiry, last run, and next window.

Installed with the rest

install.sh links skills/bot-builder into ~/.agents/skills and commands/bots.md into ~/.agents/commands. A Captain started before that install cannot load either; restart it with fm.

Activation and the unchanged daily flow

A new bot does not run until the watcher check exists. Activating it is a separate, explicit instruction:

fm bot check-install

That writes $FM_HOME/state/bots.check.sh and binds it with FirstMate's own bin/fm-check-register.sh bots. Its bytes pin the checkout it ran from, so run it from the checkout the home should use. Retire it with FirstMate's bin/fm-check-unregister.sh bots.

  1. Due. While a bot is inside its window and its dated id <name>-<YYYYMMDD> (Stockholm date) is not yet filed, the check prints bot due: <id> spec=… level=…. A missed window is never filed later, the same day or the next: nothing happens until the bot's next scheduled occurrence.
  2. File. The Captain runs fm bot file <id>. It re-checks the spec, files the id through the official backlog with the plan in the row's body, records a durable marker under data/bots/.filed/, and prints the dispatch plan. A raw backlog add would skip that marker.
  3. Dispatch exactly the plan. Role file, route, kind and delivery, scope, limits, excluded paths, access, wall-clock limit, and stop rule go into the brief as printed. The Captain never widens the scope or raises the level.
  4. Silent for the rest of the day. The marker keeps the bot quiet even after the dated task is done and pruned from the backlog the same day.

A second fm bot file of a filed id prints already-filed: <id>: dispatch nothing. The one exception is the live Captain session that printed the plan itself asking again before anything was dispatched: it gets already-filed (planned in this session, not started): <id> and no second plan, because its earlier plan is still valid - dispatch that plan exactly once (its stored copy is the row body in fm-tasks-axi.sh show <id> --full). Only a filing interrupted before its plan was printed (killed during the backlog add, or a marker that could not be written) prints already-filed (queued, not started): <id> with the stored plan, once, while the row is still queued, unheld, and unstarted; dispatch exactly that plan. That recovery is not a catch-up: the id was filed in its window, so fm bot file <id> still answers it after the window closes or the day ends, and an earlier day's recovery never touches the current day's markers. An id that was never filed stays refused. Backlog writes are never killed on a timeout.

A Captain can also end after a plan was printed but before it dispatched. The plan marker records which session printed it, from FirstMate's own session lock (its harness pid and start time). fm bot file <id> prints the stored plan again, once, as already-filed (planned, dispatcher gone, not started): <id>, only when every one of these holds: it runs inside the session that now owns the lock; the recorded session is not a live harness started at the recorded time; the row is still queued, unheld, and unstarted; and official fm-spawn left no record for the id (task record, git-hooks strip, busy or pending-close record, worker status or turn marker). A plan printed outside a lock-owning session, a live printer, a started or held row, or any such record always answers already-filed:. There is no time-based retry.

Other check lines: bot invalid: … files and holds the id for the Captain through FirstMate's fm-captain-hold.sh, with its cause and no plan; an unreadable, symlinked, directory, or FIFO spec is reported and filed this way without being followed or read. bot error: … reason=invalid-unheld means an invalid bot's filed row is not held yet, so run fm bot file <id> again to hold it. Any other bot error: … is a broken check reported as a wake, never silence; a per-bot backlog-unavailable or check-failed-* line prints once per occurrence, so an identical repeat from the previous sweep that day stays quiet and cannot starve later checks. A sweep starts no bot after 15 seconds and names the bots it did not reach; the watcher's 30-second limit is unchanged, with read, lock and native timeout overhead consuming the remaining margin. Deferred bots are evaluated first by the next sweep that day, and each 5-minute slot also starts one bot further along, so a deferred bot waits at most one sweep while the budget can reach it. check-install removes the new file when registration fails or times out, or restores the previous check's bytes and registers them again through FirstMate's own register, and says so if that fails; it never writes a trust record itself. A non-UTF-8 byte in captain.md spoils only its own line: a record holding one no longer matches, so a push bot downgrades.

Permission levels

A level is an upper bound the spec may claim, never an approval. Any commit and any push still needs the Captain's own approval for that commit.

LevelA runThe spec additionally needs
local-proposalA read-only scout report with dated findings. No branch, file, or commit change.Nothing beyond a valid spec.
local-commitA local-only ship on bot/<name>/<occurrence-id> within the limits, left uncommitted, ending in needs-decision [key=commit-approval].The Captain's exact authorization words, their scope, the day they were given, an expiry date, and file and line limits. The project's registered posture must allow it; a local-only project allows at most this level.
pushAs local-commit; a push only after its own approval.Everything above, plus excluded paths, one remote, a branch prefix ending in / (bot-builder uses bot/<name>/), at most one push per run, a project without +yolo, authorization words naming the bot and the project as whole words, and a dedicated record of those exact words in $FM_HOME/data/captain.md: a line bot-authorization: <words>. Matching prose elsewhere in the file does not count.

New mutating plans carry branch_prefix and branch: the branch is that prefix plus the full occurrence id, matching FirstMate's supported ship contract. Pass the printed --branch-prefix to both fm-brief.sh and fm-spawn.sh. Local-commit uses bot/<name>/; push retains the spec's validated push_branch_prefix. For example, prefix bot/nightly/ and id nightly-20261022 produce bot/nightly/nightly-20261022; interval and remote ids are appended in full too. Report-only plans have no branch or prefix.

Previously filed plans and receipts are not rewritten by this correction: recovery returns their original stored plan, not a regenerated name. An incompatible legacy plan needs an explicit authorized amendment before dispatch, preserving the original plan and filing history. Do not rename its task, file a duplicate, or backfill a missed occurrence.

create refuses any gate failure. The due evaluation re-checks every gate each time: an elevated bot whose gate fails that day - expired, missing, or insufficient authorization, a lost Captain rule, a tightened posture - runs at local-proposal and the plan says why.

The scout role is report-only: it collects facts about a codebase or a handed PR and never reviews or changes anything. create refuses a scout above local-proposal (role-report-only), and a scout spec that claims a higher level later is bot invalid: - filed and held for the Captain with no plan, never run as a ship. The role file is instructions, not a sandbox: this gates what is filed and dispatched, not what a running worker's shell can do.

Elapsed intervals and selected remote branches

Choose exactly one schedule: a daily window, --every-hours N, or --on-remote NAME --on-branch BRANCH. New modes use the same check → fm bot file <id> → ordinary FirstMate dispatch path. They require an advisory --wall-clock-min of 1..60, never a hard execution deadline.

One admission owner, no overlap or catch-up queue

data/bots/.admission/<name>.json retains the latest candidate disposition separately from the last owned filed job. Per-bot locking serializes checks, filing and spec mutation. Admission is checked again immediately before the native backlog add; a reserved interrupted add is reconciled against the stored native plan, not blindly retried. Missing, malformed or mismatched continuity fails closed; removing/recreating a spec does not reset it or migrate a daily bot.

A queued, inflight, held, busy, timed-out/unfinished or uncertain predecessor permanently skips this bot's current occurrence. Completion later cannot replay it. due --json shows the skip and reason; the check emits no dispatch wake for a skip. Encountering a pre-existing unowned candidate row blocks new work instead of adopting it; raw external filing is never a supported bypass. Only an owned queued, unheld, unstarted plan can use the existing interrupted/dead-dispatcher recovery, with current routine and authority revalidated.

Positive finish needs a matching unheld native backlog done row and stored plan, plus either exact task/project/kind/worktree metadata with stable spawn_gen/busy_gen and trusted native adapter idle evidence, or normal retirement of metadata, busy records and the pending-close marker. Native close removes those runtime records before marking the row done, so successful cleanup does not require impossible live metadata. Idle alone, record absence alone, status prose or a dead PID never proves completion; surviving busy/pending-close state remains uncertain.

Once completion was positively observed, its saved observation can survive normal cleanup and later backlog pruning while matching idle ownership or retirement remains valid. A new incarnation invalidates the old completion clock. A row pruned before any positive observation stays unknown: current native show/list does not query archives, and no receipt is fabricated from disappearance.

The next job waits at least two hours after finish was first observed, using both UTC and local monotonic elapsed time, not filing time. This intentionally waits longer than two hours between starts and can skip extra slots. Clock jumps cannot turn a filing label into a start receipt; a monotonic reset re-anchors the wait, and a backward candidate cannot replay an older slot. There is no forced stop, hard one-hour cap, provider/detached-resource cancellation proof or protection against out-of-band manual worker restarts.

New-mode subprocess reads share a ten-second inspection budget (at most five seconds per read), with bounded per-bot lock waits and the native Git termination margin. The existing watcher remains unchanged; read budgets are not worker execution deadlines. Inspection errors wake an operator instead of authorizing dispatch.

Elapsed interval

--every-hours 3 stores an immutable UTC-seconds creation anchor. The first candidate is three hours after that anchor; subsequent boundaries are anchor + k × three elapsed hours. Late inspection selects only the latest boundary, never a backlog of missed jobs. Its identity is <name>-i<YYYYMMDDTHHMMSSZ>. Restart and pause/resume retain the anchor; resume considers only the latest current boundary. Stockholm DST changes local display, never elapsed spacing. Before the first boundary the verdict is not-yet. Every candidate still passes the shared predecessor/spacing guard; a skipped boundary stays skipped.

Selected remote branch

The existing $FM_HOME/projects/<project> shorthand must resolve to a Git checkout root. Creation pins its real path and one effective configured remote URL by hash without copying a possibly credential-bearing URL into the spec. Supply a configured remote name and exact branch, never a URL, command, wildcard or compound expression. Local files, HTTPS and SSH are allowed; custom helpers, insecure HTTP, credential changes and interactive prompts are not. No webhook, global Git hook, PR-open/update trigger or arbitrary cron expression is added.

Observation uses bounded, noninteractive native git ls-remote --exit-code --refs for exactly refs/heads/<branch>, within a shared five-second Git budget. It checks the configured binding before and after inspection, never substitutes the default branch, and never fetches, pulls, resets, pushes or changes project refs.

The first observation establishes a baseline, not a job for old history. A different successfully observed tip increments a durable sequence; unchanged/concurrent/restarted observations reuse <name>-r<12-digit sequence>. One data/bots/.observed/<name>.json retains baseline, latest OID, timestamp and sequence. Unfiled intermediate observed tips coalesce to the latest; unobserved intermediate tips are unknown. A tip skipped while busy or inside the spacing bound never replays merely because the worker becomes idle. Only a later observed tip change is a fresh guarded opportunity. A rewrite or return to a formerly observed OID is also a change from the immediately previous tip, not proof of ancestry. Paused checks observe nothing; resume compares the current tip with the preserved observation.

Remote deletion, network/timeout, malformed or multiple ref responses, changed binding or unreadable observation state reports an error and preserves the accepted observation. Observation is not a successful-work marker. No count or marker claims that superseded, skipped or filed commits were reviewed.

Exact commit handoff

Eligible filing fetches the exact observed OID into a task-private bare repository at data/bots/.artifacts/<id>/source.git, not the project's object store. It verifies a commit object and its tree and pins refs/fm-bot/observed; an unavailable or mismatched object refuses filing without marking work successful. The plan carries selected remote/branch, baseline/observed OID, artifact commit/tree, depth two and runnable git show arguments.

The Captain carries the plan's source_rule into the ordinary worker brief: inspect that immutable commit, state the actual inspected OID, and never silently use an unrelated checkout or call old observed bytes the latest. The artifact does not retarget the native worker worktree. Before source edits, prove its HEAD matches the observed OID or stop for a decision. Depth-two history is not a complete ancestry/range proof: ambiguous or insufficient history also needs a decision, not a guessed comparison. Private artifacts remain available for the task; no automatic cleanup deletes unlanded work.

Create without activation

fm bot create every3h --role senior-fullstack --project sandbox --route "EXPLORE #2" \
  --every-hours 3 --scope "Report selected project findings" --wall-clock-min 60
fm bot show every3h
fm bot create branch-scan --role code-reviewer --project sandbox --route "REVIEW #2" \
  --on-remote origin --on-branch selected --scope "Report selected branch changes" --wall-clock-min 60
fm bot due --json

These examples create specs only and keep daily role/route/level/access/approval boundaries. They do not install a check. show/list do not contact remotes; real-clock due may record observations, completion evidence and skips. A synthetic --now without the explicit test clock writes nothing. Creating/resuming a bot while a check already exists can make it eligible on that check's next sweep: obtain separate live-home authority first.

New-mode behavior is covered by hermetic CLI/native-owner and local-bare-Git fixtures, not a live assigned-worker trial or elapsed-time soak. The older daily beta evidence below is not new-mode execution evidence. No native lifecycle mechanism or hard-duration claim is added.

fm bot commands

fm bot create NAME --role R --project P --route "CATEGORY #N"
              --at HH:MM --until HH:MM [--days daily|mon,tue,...]
              # alternatively: --every-hours N
              # or: --on-remote NAME --on-branch BRANCH
              --scope TEXT --wall-clock-min N
              [--access none|secret:REF] [--notify report|needs-decision-on-high]
              [--max-candidates N] [--max-files N --max-lines N] [--exclude PATH ...]
              [--level local-proposal|local-commit|push]
              [--authorization "captain's exact words" --authorization-scope TEXT
               --authorized-on YYYY-MM-DD --expires YYYY-MM-DD]
              [--push-remote R --push-branch-prefix PREFIX/ --push-max-per-run 1]
fm bot list [--json]
fm bot show NAME [--json]
fm bot pause NAME | resume NAME | remove NAME
fm bot due [--check] [--json]
fm bot file OCCURRENCE-ID [--json]
fm bot check-install

list, show, and due take --now ISO to pin the clock; create and file accept it only under FM_BOT_TEST_CLOCK=1, because a pinned clock there could file a future day early. due is a dry evaluation: it never files, dispatches, or calls a model. On the real clock it records today's filed marker once the backlog shows today's id; with --now (and no test clock) it writes nothing at all, so a query into another day never moves today's marker. --check is the watcher form that prints only actionable lines and always exits 0. list shows next paused for a paused bot and the next day once today is filed. A refusal prints refused (<code>): <reason>. fm doctor reports the installed check's health as runtime.bot_check: its interpreter, its fm-bot, its home, its FirstMate checkout, and its registration.

Operator beta

Bots ship as a beta. Verified before landing: real-model runs of one wake → one filing → one dispatch → report → official close → a silent next sweep, a Captain asking fm bot file again for its own plan (it keeps that plan and dispatches it once), and recovery after a Captain that died between its plan and its dispatch; plus lab runs of duplicate refusal, invalid holds, several bots in one sweep, and check re-registration. Consecutive days were proven with a simulated clock only; a real multi-day run had not finished, so elapsed days on a real home are what this beta checks.

  1. Create one report-only bot (the default level, local-proposal): fm bot create NAME --role R --project P --route "CATEGORY #N" --at HH:MM --until HH:MM --scope TEXT --wall-clock-min N. The window is Europe/Stockholm wall-clock minutes, both ends included, at least 10 minutes, and never across midnight.
  2. Inspect with fm bot show NAME, fm bot list, and the dry fm bot due.
  3. Activate with fm bot check-install from the checkout the home uses, then confirm fm doctor reports runtime.bot_check as PASS.
  4. Watch the Captain answer each bot due: wake with fm bot file <id> and dispatch the printed plan, day after day.
  5. Stop with fm bot pause NAME or fm bot remove NAME; retire the check with FirstMate's bin/fm-check-unregister.sh bots.

Report as a defect: a bot due inside its window that never wakes while the watcher is armed; two plans or two dispatches for one id; a filing outside the window or for a missed day; a queued bot task left undispatched after a Captain restart. Known limits: the watcher sweeps about every 5 minutes, so a wake arrives about 1.5 to 2.5 minutes into the window and one in the window's last half minute is refused and files nothing; a dispatch aborted by FirstMate can leave its tmux window behind, which a later dispatch of that id refuses until it is cleared; the bash, credential, and same-user limits in Safety apply to bot workers too.
