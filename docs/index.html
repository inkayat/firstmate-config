Overview

firstmate-config is a reproducible configuration layer around the official FirstMate checkout. It chooses the Captain runtime, routes worker tasks to harnesses and models, installs shared skills and role agents, and keeps machine state out of Git - without forking or patching FirstMate.

When you run fm, this is what happens:

  1. The launcher loads ~/.config/firstmate-config/env, selects the Captain harness (OMP unless you pass --harness pi), and runs a preflight.
  2. It walks captain-startup-models.tsv in order and picks the first model that is not known to be unavailable.
  3. It changes into the official FirstMate checkout, so FirstMate's own AGENTS.md is the only global instruction file the Captain loads.
  4. The Captain follows primary-policy.md for each task: resolve the project, read that project's own instructions, pick a dispatch category, a role, and at most a few skills, then hand the work to an isolated worker.

When to use it

Use it when you run a FirstMate fleet on your own machine and want the setup to be repeatable: the same Captain model chain, the same routing, and the same pinned skills on every machine that runs fm update.

It is not a standalone agent, a project template, or a place to keep project knowledge. Each project keeps its own AGENTS.md, CLAUDE.md, and project-local skills, and those outrank everything configured here.

What you get

  • OMP-first Captain with an explicit Pi fallback, and a startup model chain that falls back on a known-unavailable model.
  • Semantic routing across eleven dispatch categories, kept in one JSON file.
  • Twelve roles - three core, five specialists, four for an opt-in single-task team - that double as OMP agents, and pinned shared skills, all layered below project instructions.
  • Read-only diagnostics: fm doctor and fm version.
  • Fast-forward-only updates of both checkouts with fm update, followed by an idempotent reconcile.
  • A Kanban board that projects live FirstMate work with fm board.
  • Scheduled bots: daily routines filed as ordinary tasks, with permission levels that never replace per-commit approval.

Tips

Check before you trust

Run fm doctor after installing and after every fm update. It is read-only and tells you which part of the stack is outside what this configuration was validated against.

A running Captain does not reload

The Captain keeps the instructions and wiring it loaded at startup. After an update, end the session and run fm again.

Planned work is not documented here

The repository README has a roadmap (for example optional multi-agent deliberation). Nothing on it is current behavior, and this guide does not describe it.
