Safety and trust boundaries

This configuration changes the behavior of every project on the machine, so it is built to be reviewable, pinned, and quiet. This page lists what it will and will not do, and where its guarantees stop.

Boundaries by component

ComponentBoundary
Official FirstMate checkoutUpstream-clean. Never modified, except by the fast-forward-only first stage of fm update. install.sh reports a modified checkout and leaves it alone.
Project repositoriesThe installer never touches them. Project knowledge is never copied into this repository; it is resolved per task, in place.
CredentialsNever stored. Authentication, sessions, and runtime records live outside the repository.
Existing files at link locationsIf a file or directory already sits where a symlink belongs, the installer warns and leaves it alone. An existing symlink that does not already reach the expected source inside this checkout or the skill cache is reported as a failure and never rewritten, whoever made it. In OMP's agent root it also leaves alone, with a warning, any fm-<role>.md symlink that does not point at a firstmate-config file, and never touches other agent files.
$FM_HOME/data/captain.mdSeeded once, then owned by the machine. Never overwritten.
SecondmatesA secondmate home is refused as a Captain home, and fm update does not update secondmates.
BotsNothing runs until fm bot check-install activates the watcher check, and each run is an ordinary FirstMate task. A level is an upper bound, never approval: every commit and every push still needs your approval for that commit. Access fields hold secret reference names, never secrets.

Read-only commands

fm doctor and fm version never install, repair, or restart anything, never modify FM_HOME, projects, or the official checkout, and never make a paid model call. Their Git probes run with optional locks disabled so they cannot write an index refresh or ref lock into a repository they only inspect. ./install.sh --verify likewise reports drift without changing anything.

Availability checks answer "do credentials resolve?". They do not prove a key is valid right now or that quota remains.

Update safety

  • The official checkout's origin must be exactly firstmate_repo from the manifest. A different URL, or an insteadOf rewrite, is refused before the remote is contacted.
  • Only fast-forwards. Nothing is forced, stashed, reset, merged, rebased, discarded, or pushed.
  • Both checkouts are checked before either changes. A refusal leaves both exactly as they were.
  • Failures after the official fast-forward are reported as a PARTIAL UPDATE, never as success.

Details and recovery are on Update and recovery.

Pinned dependencies

  • External skills are pinned by full commit hash in skills/external.lock. A branch is never tracked, because that would change behavior on every project without a visible diff.
  • Nothing is vendored, so upstream licenses stay with their sources.
  • Pins move only through a visible edit. ponytail-update prepares one, shows the diff, runs the tests, and stops before committing.
  • Pi's Ponytail package is a separate pinned checkout, so a later pi update cannot mutate the shared skills.

Worker isolation

  • Each task runs in its own isolated worktree, never in the Captain's checkout, so what one task reads does not leak into another.
  • Only FirstMate orchestrates across projects. A worker never switches to another registered project, creates an independent FirstMate task, or modifies a primary checkout outside its own task.
  • With OMP, a worker may use the harness's own bounded task tool for a task-local helper. The helper stays inside the same task, project, and worktree and inherits the parent's boundary; the parent remains responsible for the result. Pi has no equivalent mechanism and does not spawn workers.
  • The Captain's standing instruction asks it to confirm before anything destructive outside a task worktree.

Project rules win

Project-native instructions and project-local skills outrank every role and every shared skill here. A shared skill that conflicts with a project rule loses. See Precedence.

Review

The selected official FirstMate delivery path owns review, fixes, and verification; this configuration adds no review requirement of its own and never stacks a manual reviewer on top of no-mistakes. Official FirstMate allows a separate review or audit only when you explicitly request it or the authorized task is itself a knowledge-only review. This configuration adds only how such a review runs: scoped, read-only, working from a diff or patch with its base and head revisions, never fetching, pulling, or updating a canonical checkout, and with no authority to fix, publish, or merge. Findings are BLOCKER, IMPORTANT (only you waive it), and OPTIONAL.

Whether a request selects no-mistakes is decided by official FirstMate intake and its own skill, not by this configuration; when it is selected, it alone owns review and no manual reviewer is stacked on it. Asking for tests or a smoke run grants no commit, push, or publication authority by itself. If a task needs more rigor than its delivery path gives, the question escalated to you is whether to use no-mistakes.

What is not guaranteed

Be precise about these
  • Context and skill selection are policy and handoff mechanisms. They are not proof of read order, compliance, or task completion.
  • There is no trusted verification runner or FirstMate completion hook in this configuration. A passing fixture report does not stand in for verifying the actual change.
  • The routing and skill trace is a diagnostic. Its citation check is a lexical match and cannot prove the right category was chosen or that a skill was applied.
  • fm update has no multi-repository rollback.
  • A running Captain is not notified of updates and keeps what it loaded at startup.
  • fm doctor's runtime task-staleness check reports UNKNOWN when tasks are in flight, because no safe bulk read-only classifier exists. Use FirstMate's per-task state check for an authoritative answer.
  • Role rules such as "own paths only" or "write no files" are instructions, not a sandbox: bash can still write, read, and use every credential wherever the operating-system user can. There is no OS sandbox, worker-specific credential, or branch protection.
