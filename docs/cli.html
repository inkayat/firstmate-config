CLI reference

Everything here exists in the repository's scripts. fm is the single entry point; it dispatches doctor, version, update, board, bot, and team to their own scripts.

fm

fm [--harness omp|pi]
fm [--harness omp|pi] --check
fm [--harness omp|pi] --print-command
fm --help

Starts the Captain on OMP by default. Before the harness starts it runs a preflight; it stops with an fm: error if the FirstMate checkout has no AGENTS.md, a primary extension or the startup model file is missing, the harness executable is not on PATH, the herdr CLI is missing while the backend is Herdr, or FM_HOME is a secondmate home.

OptionPurpose
--harness omp|piSelect the Captain harness. Must come first. Also valid before doctor and version.
--checkRun the preflight and model resolution, print the resolution as KEY=value lines, end with PREFLIGHT=ok, and exit without starting anything.
--print-commandSame as --check, plus a COMMAND= line with the exact harness command.
--help, -hPrint the launcher's header documentation.

Any other argument is rejected: unknown argument '...'; see fm --help. A normal launch prints the harness, the preferred and selected model, and availability, then execs the harness.

fm doctor

fm doctor
fm doctor --json
fm --harness pi doctor

A read-only report across the whole stack. It never installs, repairs, or restarts anything and never makes a paid inference call. Output is grouped into sections: SYSTEM, LAUNCHER/PATH, CAPTAIN, RUNTIME, HARNESSES, ROUTING, ROLES, SKILLS, PROJECTS, and OTHER. Each line is a status, a check id, and a summary:

CAPTAIN
  PASS          captain.harness                  selected Captain harness: omp
  PASS          captain.selection                selected preferred candidate openai-codex/gpt-6.1-sol (medium)

RUNTIME
  PASS          runtime.herdr_server             herdr server running (version X, client X)
  WARNING       runtime.herdr_version            herdr server X is newer than the tested baseline Y; unvalidated

DOCTOR PASS exit=0
StatusMeaning
PASSHealthy.
WARNINGWorth reading; does not break the architecture. Examples: a tool newer than the tested version, or an unavailable startup candidate while another one is selected.
FAILA failed check. Only some failures are mandatory and change the exit code.
UNKNOWNThe probe ran but could not decide. Doctor does not guess.
DEFERREDIntentionally absent for now (the Qwen/Ollama lane).
NOT_APPLICABLENothing to check, for example no confident current project.

Exit status

0 when the mandatory architecture is healthy, even with WARNING, UNKNOWN, or DEFERRED present. 1 on a genuine mandatory break:

  • the official FirstMate checkout is missing or broken, or at a known-incompatible commit (behind the validated baseline, or diverged);
  • the stack manifest, captain-startup-models.tsv, or crew-dispatch.json is missing or invalid;
  • there is no usable Captain: missing executable or primary extensions, an empty chain, or every candidate unavailable;
  • the Herdr CLI is missing, its server is unreachable, incompatible, or not running;
  • Pi, OMP, or Herdr is below the manifest's hard minimum;
  • an expected fm is shadowed on PATH by a different executable earlier in PATH.

JSON

--json prints one object. Top-level keys: schema_version, status (the worst check status), exit_code, timestamp, system, firstmate, launcher, captain, runtime, harnesses, routing, roles, skills, projects, and checks. Each entry of checks has an id, a status, and a summary, plus a detail when there is one.

fm doctor --json | jq -r '.checks[] | select(.status != "PASS") | "\(.status)\t\(.id)"'

A fast identity summary - not a health check, and it makes no availability probes. Use fm doctor for a verdict.

The versions shown are examples. --json returns the same facts as one object with firstmate_config, firstmate, components, captain_harness, stack_manifest, fm_home, platform, and architecture. Version strings read unknown when a tool is missing.

fm update

fm update

Takes no options other than --help. Fast-forwards the official FirstMate checkout, then this repository, then runs ./install.sh and ./install.sh --verify. Exits nonzero on a refusal or failure. The full behavior, the refusal table, and recovery are on Update and recovery.

fm board

fm board
fm board --lavish

Opens the persistent Kanban board; it is shorthand for fm-board open. See Task board.

fm bot

fm bot create NAME ...   # see Bots for every flag
fm bot list | show NAME
fm bot pause NAME | resume NAME | remove NAME
fm bot due [--check]
fm bot file NAME-YYYYMMDD
fm bot check-install

Shorthand for bin/fm-bot. It never spawns a worker or calls a model: due is a dry evaluation, and file files today's due id and prints the dispatch plan for the Captain. check-install activates the watcher check and is a separate, explicit step. Full options, levels, and the daily flow are on Bots.

Like every fm subcommand, fm bot and fm team act on the env file's FM_HOME, not one exported in your shell (Configuration). For a lab or other home, call bin/fm-bot or bin/fm-team directly with FM_HOME, or point FM_CONFIG_ENV at that home's env file.

fm team

fm team validate PROFILE.json
fm team bind TASK --profile NAME --base COMMIT
fm team check TASK
fm team audit TASK [--worktree PATH]

Shorthand for bin/fm-team. validate checks a profile against the real role frontmatter and prints every refusal as refused (code). bind validates teams/NAME.json, snapshots it for the task, and warns when the policy extension is not linked, because then nothing enforces it at runtime. check prints none, team, or a refusal such as team-profile-tampered; it is the relaunch check. audit lists every committed, staged, unstaged, untracked, deleted, and renamed path since the bound base and exits nonzero on a path outside the team scope, a symlink leaving the worktree, or a gitlink. It never spawns, commits, pushes, or merges. See Team profiles.

ponytail-update

ponytail-update

Takes no arguments. Requires the firstmate-config checkout to be on a clean main that can fast-forward with origin/main. It pulls fast-forward only, checks the latest stable Ponytail release, and, if one is newer, updates skills/external.lock, prints the diff, runs tests/update-ponytail.sh and tests/pi-ponytail-package.sh, applies the pin with ./install.sh, verifies, and checks again. It never commits, merges, pushes, creates branches, or tags. If already current, it reports UPDATE_APPLIED: false and stops.

install.sh

./install.sh            # reconcile
./install.sh --verify   # report drift, change nothing

Exits nonzero if any step reports FAIL. The final line is install: N change(s), M failure(s), or with --verify, verify: N drift item(s), M failure(s). See Installation and first run for the steps.
