Installation and first run

One clone, one idempotent script. Running ./install.sh again is the normal way to reconcile a machine, not a special case.

Requirements

The installer checks the toolchain first and stops before changing anything if a required tool is missing.

ToolStatusWhy
gitrequiredClones, fast-forwards, and pins everything.
omprequiredDefault Captain harness and the harness for most workers.
pirequiredExplicit Captain fallback and the harness for Pi-routed workers.
herdrrequiredThe runtime backend. The launcher also refuses to start without it while FM_BACKEND=herdr.
jq, treehouse, gh, bunrecommendedMissing tools only print a warn line; they are needed for full fleet behavior.
python3conditionalNeeded to reconcile Pi's Ponytail package settings (step 9) and the Agent Library (step 10, and its --verify, fm doctor and fm version checks).

Minimum and tested versions of Pi, OMP, and Herdr live in firstmate/stack-manifest.tsv. fm doctor compares your installed versions with it; a newer tool is a WARNING, a tool below the minimum is a FAIL.

Install

git clone https://github.com/inkayat/firstmate-config.git
cd firstmate-config
./install.sh
Run it from the clone you intend to keep

The installer points fm, the dispatch file, and the skill, command, and role-agent links at the checkout it runs from. Do not run it from a throwaway worktree.

It works through ten numbered steps. Every step states a desired end state and changes only what differs:

  1. Toolchain - the checks above.
  2. Official FirstMate checkout - cloned to FIRSTMATE_ROOT and pinned to the validated commit only if it is missing. An existing checkout is reported against the baseline (ok, or a warn if ahead, behind, or diverged) and never modified.
  3. Operational home - creates state, data, config, and projects under FM_HOME.
  4. Environment file - writes ~/.config/firstmate-config/env with the resolved paths.
  5. Runtime backend - sets $FM_HOME/config/backend to herdr.
  6. Dispatch and Captain file - symlinks crew-dispatch.json into $FM_HOME/config/ and seeds $FM_HOME/data/captain.md once; an existing copy is never overwritten.
  7. Global skills, commands, and role agents - links this repository's skills and the pinned external skills into ~/.agents/skills, its slash commands (commands/*.md, such as /bots) into ~/.agents/commands, and each role file into ~/.omp/agent/agents/fm-<role>.md. A file or directory already at a link path is reported and left alone; so is a role-agent symlink that does not point at a firstmate-config file.
  8. Launchers - links fm and ponytail-update into ~/.local/bin and warns if that directory is not on PATH.
  9. Pi Ponytail package - a separate pinned checkout for Pi, with a skills filter so its bundled duplicates never shadow the shared ones.
  10. Agent Library - the version pinned in the stack manifest, installed at ${XDG_DATA_HOME:-$HOME/.local/share}/agent-library, the root fm discovers when AGENT_LIBRARY_ROOT is unset (below). Skipped with a warn when the manifest pins no Library.

Every link the installer creates is relative to its own directory, so a HOME that moves or is spelled differently on another machine keeps it valid. A source is linked only when it exists inside this checkout or the skill cache; one that is missing or resolves outside them is reported as a failure and never linked. An existing link whose chain reaches that same source without leaving its tree - absolute, as older installs wrote them, relative, or through an alias inside the tree - is left exactly as it is, never rewritten for its spelling. Any other existing link - wrong, broken, or through an alias outside the tree - is reported as a failure by --verify and a normal run alike and is never rewritten; remove it and run the installer again to link it.

A trimmed run on a settled machine looks like this:

1. toolchain
  ok      git present
  ok      omp present
  ...
2. official FirstMate checkout
  ok      present at ~/Developer/tools/firstmate
  ok      matches the validated baseline commit 
...
7. global skills, commands, and role agents
  ok      ~/.agents/skills/systematic-debugging
  ok      ~/.agents/commands/bots.md
  ok      ~/.omp/agent/agents/fm-senior-fullstack.md
  ...
8. command launchers
  ok      ~/.local/bin is on PATH

install: 0 change(s), 0 failure(s)

Lines are prefixed ok, changed, warn, DRIFT (only with --verify), or FAIL. A FAIL makes the script exit nonzero.

The Agent Library step

The pin is three rows in firstmate/stack-manifest.tsv: library_repo, library_commit and library_tree (full object ids). An optional library_ref (refs/tags/<name>) is only a fetch fallback for a server that refuses a fetch by commit id; whatever it brings, only the exact pinned commit and tree are ever accepted. A branch head is never followed: the Library moves only when a reviewed manifest change moves the pin.

Everything step 10 owns lives under the data home D=${XDG_DATA_HOME:-$HOME/.local/share}, outside every checkout:

  • D/agent-library - the active pointer, a relative symlink .agent-library/<commit>. It is only ever replaced by one atomic rename, so it always names a complete, verified version.
  • D/.agent-library/<commit>/ - one immutable directory per installed version. Older versions are kept; nothing deletes them.
  • D/firstmate-config/agent-library.receipt - the receipt: which versions, pointer and directory this installer created, by device, inode and link text, with a checksum.
  • D/firstmate-config/agent-library.lock - the lock anchor, created once and never unlinked or recreated.

A run takes an exclusive, non-blocking lock on the anchor; a second installer on the same machine stops at once with another installer holds the Agent Library lock and changes nothing, and the kernel releases the lock if a run dies. Under the lock it reads the receipt, finishes or drops a switch an interrupted run recorded, and then, unless the pinned version is already active and still rebuilds its tree (a no-op with no write at all):

  1. reuses a retained verified version, or fetches only the pinned commit (non-interactive) into the source cache and checks its commit and tree ids;
  2. exports every file, mode and symlink into a private staging directory and rebuilds the pinned tree id from the exported bytes - any difference stops the run and removes that staging directory;
  3. gives the export its version name and records it in the receipt;
  4. records the coming switch durably, re-checks every identity, renames the new pointer over the old one, and finalizes the receipt.

If the run stops before the rename, the previous version stays active. If it stops after the rename but before the receipt is finalized, the new, already verified version is active, the previous one is retained, and the receipt still says the switch is pending: --verify reports receipt finalize pending and the next run completes it.

Refusals. Ownership is what the receipt records, never a name or a shape. A pointer, version directory or receipt that is present but not recorded - a same-looking symlink, a copied directory with a new inode, a missing, truncated, invalid or edited receipt, a lock anchor that is a symlink, directory, hard link or foreign file - makes the step fail with nothing adopted, rewritten or repaired. So does an installed version whose bytes no longer rebuild its pinned tree, and a recorded version that is gone. These are damage cases for a human: inspect what is there, then remove the entry the message names; or, when the receipt no longer matches what is on disk (for example a retained version deleted by hand), remove D/agent-library, D/.agent-library/ and the receipt together - leaving the lock anchor - and run ./install.sh again for a fresh install. Retained versions are not meant to be deleted by hand; there is no supported way to reclaim them yet.

Fetch and credentials. The pinned source is a private repository, so each machine needs its own Git read access once - a credential helper (macOS Keychain, or gh auth login followed by gh auth setup-git on Linux) or an SSH key. Nothing about it is stored in the manifest or a URL; a library_repo with URL credentials is a manifest error. Without access, the step fails with a named fetch error, install.sh exits nonzero (so fm update fails too) and any installed version stays active and unchanged. With no Library installed at all, fm simply finds none and tasks keep the normal FirstMate behavior.

Rollback. ./install.sh --library-rollback runs only this step: it re-verifies the receipt's retained previous version and switches to it with the same protocol. It records no hold - --verify reports installed <previous> != pin <pin> as drift and fm doctor a WARNING until the next ./install.sh or fm update, which returns to the pin by reusing its retained version without fetching. Rollback refuses while a switch is pending, or when the previous version is missing, changed or corrupt.

Runtime. An exported AGENT_LIBRARY_ROOT, even empty or invalid, still wins over the installed root, and the installer never writes that variable anywhere. fm doctor and fm version report the pin, the installed state (not installed, pinned and verified, different from the pin, update in progress, finalize pending, invalid ownership, corrupt receipt or version) and whether fm would hand the Captain an explicit root, the installed one, or none; they never create, lock exclusively or repair anything.

Verify

./install.sh --verify   # read-only drift check
fm version              # compact identity of the installed stack
fm doctor               # read-only diagnostics

--verify changes nothing and ends with verify: N drift item(s), M failure(s). A clean machine reports verify: 0 drift item(s), 0 failure(s).

fm doctor exits 0 when the mandatory architecture is healthy - warnings do not change that - and 1 on a genuine break such as a missing Captain executable, an unreachable Herdr server, another fm earlier on your PATH, or Agent Library state that step 10 refuses. See the CLI reference for the full list.

First run

Preview what the launcher will do without starting anything:

fm --check
CONFIG_ROOT=~/src/firstmate-config
FIRSTMATE_ROOT=~/Developer/tools/firstmate
FM_HOME=~/.firstmate
FM_BACKEND=herdr
FM_FORK_ORIGIN_CWD=~/src/my-project
FM_FORK_ORIGIN_IS_PROJECT=true
CAPTAIN_HARNESS=omp
CAPTAIN_CWD=~/Developer/tools/firstmate
CAPTAIN_BIN=omp
CAPTAIN_EXTENSIONS=discover
PREFERRED_MODEL=openai-codex/gpt-6.1-sol
PREFERRED_EFFORT=medium
SELECTED_MODEL=openai-codex/gpt-6.1-sol
SELECTED_EFFORT=medium
SELECTED_AVAILABILITY=AVAILABLE
...
PREFLIGHT=ok

Three fields matter on a first run:

  • SELECTED_MODEL - the first startup candidate that is not known to be unavailable. If it differs from PREFERRED_MODEL, a FALLBACK_REASON line says why.
  • CAPTAIN_CWD - always the official FirstMate checkout, wherever you ran fm from.
  • FM_FORK_ORIGIN_IS_PROJECT - whether your launch directory is a Git project. It is used only as a default-project hint.

fm --print-command prints the same resolution plus the exact harness command line. Then start the Captain:

cd ~/src/my-project   # optional: becomes the default-project hint
fm

The launcher prints the harness, the preferred and selected model, and availability, then replaces itself with the harness process.

To use the Pi fallback instead, pass the harness before any subcommand: fm --harness pi. It is explicit and never automatic.

Projects

Project registration and the task lifecycle belong to upstream FirstMate. This configuration only reads them: a task's project is resolved by an explicit path or name, then FirstMate's registry (data/projects.md), then your launch directory as a hint. The full order is on Architecture and startup. Nothing about a project is copied into this repository.

What the installer never does

  • Store a credential, or write AGENT_LIBRARY_ROOT.
  • Touch a project repository.
  • Modify the official FirstMate checkout after it exists.
  • Overwrite a file at a link location that it does not own - it prints warn ... leaving it alone instead.
  • Create or activate a bot - specs and the watcher check exist only after fm bot create and fm bot check-install.

There is no uninstall command. Removing the symlinks the installer created and the files it wrote (listed on Configuration and files) is a manual step.
